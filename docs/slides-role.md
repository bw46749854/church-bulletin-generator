# pptx 担当者ページと権限の分け方（設計）

2026-10-22 作成。10/18・10/21・10/22 の検討で決まったことをまとめた。2026-10-23 に実装し、仕組みの要約は `ARCHITECTURE.md` §20 に取り込んだ（2026-10-24）。この文書は、設計の判断・経緯・作業の記録として残す。

---

## 1. 目的

**週報に印字される内容の編集を、牧師だけにする。** pptx 担当者（4 名、当番制、Google アカウントなし）は、スライドとマスタの仕事を専用のページでできるようにする。

---

## 2. 役割ごとにできること

| 機能 | 牧師（と開発者） | pptx 担当者 |
|---|---|---|
| **週データ（週報の印字内容）の入力・保存** | ○ | **×** |
| 週の新規作成・日付の変更 | ○ | × |
| 引用聖句（スライドタブ）の入力 | ○ | 見るだけ |
| 保存済みの週の PDF を見る | ○ | ○ |
| スライドを作ってダウンロード | ○ | ○ |
| 讃頌歌・交読文のマスタ（番号と題）の追加・修正・削除 | ○ | ○ |
| 讃頌歌・交読文の pptx の追加・差し替え・削除 | ○ | ○ |
| ファイルの差し替え（テンプレ pptx・聖句の型・名簿・曲名・交読文の題・教会情報・祈り課題・据え置き文） | ○ | ○ |
| マスタ一式のダウンロード | ○ | ○ |
| 名簿を見る | ○ | ○ |
| 教会情報・祈り課題・据え置き文の、紙面の位置での「編集」 | ○ | × |
| サイトへの反映・同期 | ○ | × |
| 名簿の編集画面（未実装。作ったら） | ○ | ○ |

- 「印字される内容は牧師だけ」の線は**週データ**で引く。マスタ（曲名など）も紙面に出るが、マスタは両方が編集してよい（10/21 決定）。
- 担当者がファイルの差し替えで教会情報などを変えることは許す。誰が変えたかは記録で分かる（§7）。

## 3. 構成

```
 牧師・開発者のブラウザ                     担当者のブラウザ
        │                                        │
   受付（Access）                           受付（Access）
   名簿: shuho-editors ＋ アカウントのメンバー  名簿: shuho-slides（担当者と牧師）
        │                                        │
        ▼                                        ▼
 ┌─ Worker samplechurch-shuho ─────────┐   ┌─ Worker samplechurch-slides ─┐
 │ /input-shuho/  牧師の画面・API      │   │ /input-shuho/slides/       │
 │                                   │   │   担当者ページ              │
 │ 担当者用の窓口 ◀───────── 内線（Service Binding）── 中継（データなし）│
 │   （許可した仕事だけ）              │   └────────────────────────────┘
 │ D1・KV（データはここだけ）          │
 │ PDF は Render に頼む               │
 └───────────────────────────────────┘
```

### 用語

| 用語 | たとえ | 意味 |
|---|---|---|
| Worker | 部屋 | Cloudflare 上で動く小さなプログラム。部屋ごとに入口のアドレスがある |
| Access | 部屋の入口の受付 | メールに届く暗証番号で本人か確かめる。**Worker 単位の受付は、その Worker の全部の入口（workers.dev・独自ドメイン・ルート・プレビュー）を守る**。部屋の中をパスで区切ることはできない |
| ポリシー | 受付の名簿 | 入れてよい人の一覧。複数の受付で同じ名簿を使える |
| Service Binding | 部屋どうしの内線電話 | Worker が別の Worker をインターネットを通らずに呼ぶ。**相手の受付は通らない**。設定ファイルに書いた組み合わせだけ |
| 窓口 | 内線に出る係 | 週報 Worker 側に置く。**係ができる仕事の一覧が、そのまま担当者の権限**。一覧に無い仕事（週の保存）は、頼まれてもやり方を持っていない |

### 権限の線を引く場所

- 担当者が牧師の画面に入れないのは **受付の名簿**（週報 Worker の受付に担当者がいない）。
- 担当者が週データを書き換えられないのは **窓口の作り**（窓口に週の保存が無い）。
- コードの中で「この人は牧師か」を判定する処理は持たない。

## 4. 担当者用の窓口に置く仕事

いまの API（`src/lib/api.mjs`）の処理をそのまま使い、窓口から呼べるものを**許可の一覧**で限る（禁止の一覧ではない。牧師側に処理が増えても、担当者側には自動で開かない）。

| 区分 | 仕事 | いまの API |
|---|---|---|
| 読む | 起動時の材料（マスタ・名簿・保存済みの週の一覧など） | `GET bootstrap` |
| 読む | 保存済みの週 | `GET week/<日付>` |
| 読む | 保存済みの週の PDF | `GET pdf/<日付>` |
| 読む | 素材（歌詞・交読文・テンプレの pptx。2026-10-25 に一覧表 manifest は目次 `index/` に替わった） | `GET files/…` |
| 読む | 聖書本文・書名の一覧 | `GET bible`、`GET bible/books` |
| 読む | マスタ一式 | `GET export` |
| 書く | 曲名・交読文の題の追加・修正・削除 | `POST masters/(hymns\|readings)`、`DELETE masters/(hymns\|readings)/<番号>` |
| 書く | pptx の追加・差し替え・削除 | `PUT files/…`、`DELETE files/(hymns\|readings)/<番号>.pptx` |
| 書く | JSON の差し替え | `PUT sync/object/<キー>` のうち **`masters/people.json`・`masters/hymns.json`・`masters/readings.json`・`church.json`・`prayer-list.json`・`texts.json` だけ** |

**置かない仕事**: `POST save`、`GET week/<日付>/new`、`POST week/<日付>/rename`、`POST preview`、`POST publish`、`PUT sync/object/weeks/…`・`public/…`、`POST masters/(texts|prayer-list|church)`、同期・エンジンの診断・サイトのビルド状況。

注意: いまの「ファイルの差し替え」（JSON）は `sync/object` を通り、**週データも書ける処理**。担当者の窓口ではキーを上の 6 つに限る。

窓口に週の保存が無いことは、テストで確かめる。

**実装（2026-10-23）**: 許可の一覧と窓口の処理は `src/lib/slides-window.mjs`、テストは `tests/slides-window.test.mjs`（`npm test`）。週報 Worker の `SlidesWindow.fetch` が受け、担当者用 Worker は依頼を `…/api/<仕事>` の形で `env.SHUHO.fetch` に渡す。窓口は URL を週報 Worker の公開アドレス（var `SHUHO_PUBLIC_ORIGIN`）の `/input-shuho/api/<仕事>` に書き換えてから API に渡す（API の中では牧師の画面から来たのと同じに見える。PDF エンジンは、この URL の `/shuho-assets/` に紙面の素材を取りに来る）。API の組み立ては牧師の入口と同じ `makeApi`（`worker/index.mjs`）。

## 5. 画面

担当者ページの URL は **`/input-shuho/slides/`**（牧師の画面と同じ `/input-shuho/` の下。本番で独自ドメインに載せるとき、ホームページの URL とぶつからない）。

| 分類 | 部品 |
|---|---|
| **共通**（牧師の画面から取り出して両方で使う） | 讃頌歌・交読文のマスタと pptx の操作／ファイルの差し替え（選べる対象はページごとに渡す）／マスタ一式のダウンロード／名簿の表示／PDF の表示／スライドを作ってダウンロード／小道具（エラーの言い換え・知らせ・ダウンロード） |
| **担当者ページ用に新しく書く** | 週の選び方（保存済みの週から選ぶだけ）／引用聖句の表示（文字だけ）／ページの骨組み |
| **牧師の画面だけ** | 週の入力・保存・新規・日付変更／引用聖句の入力／サイトへの反映／同期／紙面の位置での編集 |

- 共通にするのは「2 か所で同じ意味で使うもの」だけ。見た目が似ていても意味が違うもの（週の選び方、引用聖句）は別に書く。共通の部品の中に「担当者なら」という分岐は入れない。
- スライドはいまと同じく**使う人のブラウザの中**で作る。中身の書き換えだけで組版をしないので、ブラウザによる違いは出ない（PDF をサーバーで作る理由はここには当てはまらない）。サーバーで作れないのは Worker 無料プランの計算時間（10 ms）のため。
- 2 つの Worker のコードは**同じリポジトリ**に置き、設定ファイルを 2 つにする。共通の部品は 1 か所。push で両方とも自動配置（Workers Builds のトリガーを Worker ごとに 1 つ）。
- **出力は最新のマスタから作る。** 牧師と担当者が別々にマスタを変えるので、画面を開いたときに読んだマスタ・名簿で PDF・スライドを作らない。PDF はサーバーが毎回最新から組む（いまのまま）。スライドは作る直前に最新を読み直す。確認ダイアログは作らない（2026-10-22）。

## 6. 安全のために入れるもの（2 つだけ）

1. **「誰か」を読む処理を 1 か所にまとめる。** 変更の記録（§7）に使う。Access が渡す「誰か」（`ctx.access`）は**内線の先には届かない**ので、担当者用 Worker が読んで、依頼に添えて渡す。静的ファイルの経路でも渡されない。
2. **受付を通っていない要求は断る。** 設定画面で Access をうっかり外したときに「誰でも入れる」にならず「誰も入れない」で止まるように。本番では `ALLOW_UNPROTECTED` を外す（2026-10-23 に外した。下の「週報 Worker の門番」）。

**実装（2026-10-23）**: 担当者用 Worker は `slides/worker.mjs`（Cloudflare とのつなぎ。`ctx.access` から人を読む）と `slides/relay.mjs`（中身）。
- 受付を通っていなければ、API は 403、ページは断りのページ。窓口には渡さない。
- `/input-shuho/slides/api/<仕事>` は `…/api/<仕事>` にして内線で窓口へ。誰からかはヘッダ `x-shuho-actor` に付ける（ページから同じ名前で送られてきても上書き）。**どの仕事を通すかは窓口だけが決める**（中継では選ばない）。
- 窓口は `x-shuho-actor` が無い依頼を 401 で断る（二重の守り）。書き込み（GET 以外）は `[担当者の書き込み] {who, method, path, status}` を Workers Logs に残す（§7 の記録の仕組みができるまでのつなぎ）。
- 画面のエラー（`api/client-log`）は担当者用 Worker のログに、誰からかを付けて残す（`src/lib/client-log.mjs`。週報 Worker と共通）。
- 試験: `tests/slides-relay.test.mjs`。手元で、本物の中継・窓口・API を内線でつないで確認済み。

**週報 Worker の門番（2026-10-23、`guard-1`）**: `src/lib/auth.mjs` の `accessGate` を `worker/index.mjs` の API の前に置いた。
- 受付の証明が無い・正しくない API は 403（`{error, reason}`。Workers Logs に `[受付なし]`）。人でも機械（サービストークン。PDF エンジン・サイトのビルド・`claude-dev`）でも、この受付の正しい証明なら通す。担当者用 Worker は人（メール）だけ通す（いまのまま）。
- 守るのは `api/` だけ（2026-10-23 決定）。静的アセット（画面・紙面の素材）はコードを通らずに返るが、データを入れない決まりにした（ARCHITECTURE.md §10 の 7、`tests/assets-no-data.test.mjs`）。設定でアセットも Worker に通す（`run_worker_first`）案は取らなかった。
- 例外: `public/` の GET（サイトが読む礼拝案内。公開の情報）、手元（宛先が localhost）。
- `ALLOW_UNPROTECTED` を外し、`withAuth` の「ログインなしのときに歌詞・聖書を閉じる」仕組み（`protectedOnly`）もやめた。門番を通った要求は、歌詞・聖書も含めて今どおり使える。
- 公開鍵の一覧（1 時間使い回す）に無い鍵の証明が来たら取り直す（鍵の入れ替えの直後に 1 時間断り続けないように）。
- 試験: `tests/access-jwt.test.mjs`（門番の 5 件を足した）。

**作らないもの**: Access が使えなくなったときのための差し替えの仕組み（別のログイン方法、取り替えられる部品）。D1・KV・Render・Workers 自体も同じく無料の提供に頼っており、Access だけを特別扱いする理由がない。変更が発表されたら、そのときに対応する。

## 7. 書き込みの記録と退避

`requirements-todo.md` の 2026-10-22 の項目のとおり。担当者ページと一緒に入れる。

- マスタ・ファイルへの書き込みはすべて 1 つの関数を通す。その関数が
  - 前の内容を `history/` に退避する（いまは画面からの編集だけ退避していない → そろえる）
  - 「いつ・誰が・どの入口から・何を」を記録する
- 手元（開発サーバ・recovery）も同じ関数を通り、手元の置き場に記録する（本番かどうかの分岐は作らない）。置き場所と「誰か」は入口から渡す。
- 牧師の画面に「変わりました」の知らせは出さない（記録があればよい）。

## 9. 前提と、分かっていること

### カード（支払い方法）を登録しない

| 操作 | カード |
|---|---|
| Worker 単位の Access（Worker の Access タブ） | 不要（9/20 から稼働。契約 0 件・支払い情報なし） |
| ポリシーの作成・編集 | 不要 |
| Zero Trust の「アプリケーション」画面（ホスト名・パスを指定する受付） | **必要**（開くと「プランを選択する」） |

- 2 つの受付は**同じ種類**（`self_hosted` の Access アプリ）。違うのは守る対象の指定で、Worker 単位は `{"type": "worker"}`、アプリケーション画面はアドレス（ホスト名・パス）。名簿・ログイン画面・ログイン方法は共通。
- 1 つの Worker の中をパスで分けるにはアプリケーション画面が要る → カードが要る → だから Worker を分ける。

### 独自ドメイン

- Worker 単位の Access は **routes・Custom Domains・workers.dev・プレビューのすべてを守る**（公式: Workers > Cloudflare Access、changelog 2026-08-14）。独自ドメインに載せても、アプリケーション画面は使わない。
- ホームページは `www.example.com`（公開、受付なし）。サイトへの反映は Cloudflare の API とサービストークンで動くので、入力画面のアドレスに関係しない。

### アカウント

- Cloudflare に「個人用・法人用」の区別はない。教会のアカウント（未作成）も同じ種類。いまのアカウントも作った当日に、カードなしで Access が有効になった。

### 頼っていること

- Worker 単位の Access がカードなしで使えること。Zero Trust は本来「Free でも支払い情報の登録が必要」という建て付けで、いまの状態が続くかは分からない。§6 の 2 で、なくなっても「誰も入れない」で止まる。

## 11. 次の検証（最小の仕組み）

1. 担当者用 Worker を作る。中身は、内線で週報 Worker の窓口を呼び、「つながりました」と出すだけ。
2. Worker の Access タブで、担当者用は `rehearsal-viewers`、週報用は `shuho-pastor` ＋ アカウントのメンバー ＋ サービストークン 2 つにする。
3. `pptx@example.com`（テスト用、牧師以外）でログインし、担当者用には入れて「つながりました」と出る、週報用には入れない、を確かめる。

コードはブランチで作り、配置はユーザーの確認後。

**結果（2026-10-22、コミット `d24261b` を配置）**: 3 つとも期待どおり。

- 担当者用 Worker: 受付なしでは 403（§6 の 2 が働く）。受付を付けた後、名簿にある人は「つながりました」、表示のメールも正しい → **`ctx.access` は Worker 単位の Access で渡る**、**内線（Service Binding）は本番でつながる**。
- 週報 Worker: 担当者用の名簿にだけいる人（`pptx@example.com`）は、担当者用でログイン済みでも、週報ではログイン画面に戻される（入れない）。
- ログインは共通（`your-team.cloudflareaccess.com`）なので、両方の名簿にいる人は、もう一方を開くと暗証番号なしで入れる。これは仕組みどおり。
- 名簿はユーザーが整理した: 週報 `shuho-editors`、担当者用 `shuho-slides`（`rehearsal-viewers` はホームページだけ）。§8 の名前はこれに読み替える。

### プレビューの作り方（2026-10-23 決定）

**2 つの Worker とも同じ形にした（本番移行のときと同じ形）**:
- Cloudflare の新しいプレビューの方式（Worker Previews）は**有効にしたうえで、「プレビューブランチのビルド」はオフ**。
- 代わりに、main 以外のブランチ用のビルド設定を **API で足してある**（名前「Deploy non-production branches」、main 以外で `npm run build` → `npx wrangler versions upload`。担当者用は `-c slides/wrangler.jsonc` 付き）。週報 `e13693fc…`、担当者用 `0347e933…`。
- これで preview に push すると、2 つとも**本番の Worker の別の版**としてプレビュー版ができる（本番と同じ D1・KV・シークレット）。URL は `https://preview-samplechurch-shuho.example.workers.dev/input-shuho/` と `https://preview-samplechurch-slides.example.workers.dev/input-shuho/slides/`。
- 予備: `npm run preview:slides`（担当者用を手元から出す）。

**なぜこの形か**:
- 新しい方式のプレビューは「本番の設定を使わない」（変数・シークレット・バインディングをプレビュー用に別に持つ）。シークレットはコピーになり、ベースの値を後から変えても既にあるプレビューには効かない（公式の文書 Workers > Previews > Configuration）。
- 新しく作る Worker は新しい方式しか選べない（教会のアカウントでも同じ）。古い → 新しいは一方通行。
- 新しい方式の「プレビューブランチのビルド」は、このアカウントではオンにしてもビルド設定が作られなかった（担当者用 Worker で、オフ→オン、Git の接続のやり直しでも同じ。workers-sdk #15140 と同じ症状）。
- ビルド設定の API（`POST /accounts/{id}/builds/triggers`、権限 Workers CI の編集）は公式。1 つの Worker は本番用とプレビュー用の最大 2 本を持てる（公式の文書 Builds API reference）。ただし「新しい方式の Worker でプレビュー用に `versions upload` を使う」組み合わせは、文書の想定（`npx wrangler preview`）から外れる。
- **ビルドの設定画面で「プレビューブランチのビルド」をオンにしたり、Git の接続を解除したりすると、API で足した 1 本が消える**（週報 Worker で有効化したときに消えた）。触ったら足し直す。

**教会のアカウントに移るとき**: Git を接続 → 「プレビューブランチのビルド」をオフ → 上の 1 本を API で足す（ビルド設定の書き込み権限のあるトークンで、終わったら外す）。

### 記録と退避の実装（2026-10-23）

- `src/lib/api.mjs`: 正本への書き込みは `writeObject`（JSON。前と違えば `history/` に退避）・`writeFile`（素材。前があれば退避）・`recordChange`（記録だけ。週の保存・日付の変更）を通す。記録は `meta/changes/<UTC日付>.json` に `{at, who, via, op, key, …}`。`GET api/changes?days=7`（新しい順。担当者の窓口には開けていない）。
- 対象: マスタ（画面の編集・差し替え・削除）、素材（置き換え・削除）、週（保存・日付の変更・同期での差し替え）、サイトへの反映。PDF の写しやエンジンの記録などの内部の `meta/` は対象外。
- 誰か・どの入口かは入口が `o.actor(request)` で渡す: 週報 Worker＝受付の証明のメール（`verifyAccessJwt`、var `ACCESS_TEAM_DOMAIN`・`ACCESS_AUD`）・`input-shuho`／担当者の窓口＝`x-shuho-actor`・`slides`／開発サーバ＝`local`（誰かは空）。本番か手元かの分岐は無い。
- 日ごとの表を読んで足して書くので、同じ瞬間の 2 件は片方が落ち得る（週に数回の書き込みなので許す）。
- 試験: `tests/changes.test.mjs`。手元の開発サーバで、マスタの登録・画面での教会情報の編集・週の保存・マスタの削除が `data/meta/changes/` に残り、`api/changes` で読めることを確認。
- **曲名・交読文の題は、番号ごとに前と後を残す**（2026-10-23 決定、`log-2`）: `titles: {"996": [null, "あいうえお"]}`（新規は前が `null`、削除は後が `null`）。それまでの `nos`（番号だけ）を置き換えた。
  理由: 記録を開くのは「週報の題が違う。いつ・誰が・どう変えた？」と聞かれたとき。その答えが 1 行で出る単位にする。「新規」「更新」のラベルだけ足しても「何に変わったか」は分からず、控えとの突き合わせが残る。前後があれば新規・削除も読める。題は短く、週報に印刷され、担当者も変えられる（役割を分けた理由に直結）。教会情報・名簿などの長いものは「変わった」だけにして、前の中身は控えに任せる。記録の読み方は ARCHITECTURE.md §2.6。
