## 1. 全体像

```
 牧師のブラウザ（入力画面 /input-shuho/）          担当者のブラウザ（担当者ページ /input-shuho/slides/。§20）
   │  入力は画面のメモリにだけある。                   │
   │  「保存」を押すまでどこにも残らない               │  受付（Access。名簿 shuho-slides）
   │  受付（Access。名簿 shuho-editors）               ▼
   ▼  fetch（/input-shuho/api/…）              Worker  samplechurch-slides（データを持たない。誰からかを添えて中継）
 Cloudflare Worker  samplechurch-shuho                   │  内線（Service Binding。受付は通らない）
 （worker/index.mjs → src/lib/api.mjs）                 │
   ├─ API の門番            … 受付の証明が無ければ 403（§6）
   ├─ 担当者用の窓口 SlidesWindow ◀─────────────────────┘  許可した仕事だけ。週データは書けない（§20）
   ├─ D1  samplechurch-shuho   … 週データ・マスタ・記録・ファイルの目次（表は objects 1 枚）
   ├─ D1  samplechurch-bible   … 聖書本文（読み取り専用）
   ├─ KV  samplechurch-files   … 歌詞・交読文・テンプレの中身（blobs/<指紋>）、PDF の写し（期限付き）
   ├─ PDF エンジン          … Render のコンテナ（いま）／Cloudflare Browser Rendering（予定の本番）
   └─ サイトの再ビルド       … Workers Builds API（「サイトに反映」）

 教会サイト Worker  samplechurch  ◀──┘ ビルド時に api/public/current を読んで HTML に焼き込む
```

- API のコード `src/lib/api.mjs` は、ローカルの開発サーバ（`scripts/dev-server.mjs`）と本番 Worker で**同じもの**を使う。差は、外から渡す保存先（D1 か `data/` のファイル）と PDF エンジンだけ。

### ブランチと反映（2026-10-23 決定）

| ブランチ | 役割 | push すると |
|---|---|---|
| `main` | 本番（いまはリハーサル環境） | Workers Builds が 2 つの Worker とも `npm run build` → `npx wrangler deploy`（担当者用は `slides/wrangler.jsonc`）。**そのまま本番に出る** |
| `preview` | 本番に出す前の事前確認。URL を固定したいので、いつもこのブランチで試す | `npm run build` → `npx wrangler versions upload`（担当者用は `-c slides/wrangler.jsonc`）。版ができ、別名の URL `preview-samplechurch-shuho…`・`preview-samplechurch-slides…` がその版を指す。本番の URL は変わらない |
| それ以外（作業用） | 開発ごとに随時作る。要らなくなったら時々消す | 同じく版だけできる（別名 `<ブランチ名>-samplechurch-shuho…`） |

- 流れ: 作業ブランチで作る → `preview` をその中身にする（`git push --force origin <作業ブランチ>:preview`）→ 実機で試す → 作業ブランチを `main` に入れて push（本番）→ `preview` を `main` に戻す（`git push --force origin main:preview`）。
- **事前確認の版は、本番と同じ D1・KV・鍵（シークレット）で動く**（版の URL の仕組み。§4.8 の調べものを参照）。試すときは、保存は既存の週を変更なしで行うだけにし、新しい週を作らない（残す範囲を超えた週が消える）、「サイトに反映…」を押さない（本物のホームページが変わる）。担当者ページのプレビュー版は、内線で**本番の**週報 Worker の窓口につながる（確かめられるのは担当者ページの画面まで。窓口・API の変更は手元か、牧師の画面のプレビューで確かめる）。
- **プレビューの作り方（2026-10-23）**: 2 つの Worker とも、Cloudflare の新しいプレビューの方式（Worker Previews）は有効（一方通行）にしたうえで「プレビューブランチのビルド」はオフにし、main 以外のブランチ用のビルド設定（`versions upload`）を **API で足してある**。**ビルドの設定画面でプレビューブランチのビルドをオンにしたり、Git の接続を解除したりすると、API で足した設定が消える**。足し直し方・この形にした理由は `docs/slides-role.md` §13「プレビューの作り方」。ビルドのトリガーは API で読める（`/accounts/<id>/builds/workers/<Worker の tag>/triggers`）。
- 版の URL は、ブランチを消しても Cloudflare に残る（Access が掛かっていて、本番には影響しない）。

### 2.2 KV `samplechurch-files`

| キー | 中身 | 期限 | 個人情報 |
|---|---|---|---|
| `blobs/<sha256>` | ファイル（歌詞 259 本・交読文 64 本・テンプレ一式 `template/背景.pptx`・`背景.json`・`部品/<名前>.pptx`・`式順/<礼拝>.json`。`docs/pptx-template.md`）の中身。**名前は中身の指紋で、上書きしない**（同じ中身は 1 つを共有）。どの版が今のものかは D1 の `index/`（§2.1） | なし。どこからも指されなくなったら毎朝の片付けで消える | なし（著作物） |
| `pdf/<指紋>` | **PDF の写し**（§5） | プレビューで作ったもの 1 日、保存したもの 90 日 | **あり**（紙面そのもの） |

ファイルの置き方は `docs/file-store.md`（2026-10-25）。読むときは D1 の目次の行 → 指紋 → KV の中身。KV は書いた内容が行き渡るまで最大 1 分ほどかかるが、版の名前と中身が必ず一致し、今の版は D1（書いた瞬間から最新）が決めるので、**差し替えた直後でも古い中身を掴まない**。置いた直後で中身がまだ届いていなければ 1 秒おきに 5 回まで読み直し、それでも無ければ「少し待ってからやり直してください」（503）。
`api/bootstrap` の `files`（番号ごとの元のファイル名・更新日・枚数・比率。マスタはあるが pptx が無い番号を出すため）も目次の行から作る。歌詞・交読文の pptx は、**マスタにある番号にしか置けない**（無ければ 400）。
それまで（〜2026-10-25）は名前のまま上書きし（`hymns/48.pptx` など）、一覧表 `manifest.json` と、前の中身の写し（KV の `history/`）を持っていた。

素材（`GET api/files/…`）は `Cache-Control: private, no-cache` と `ETag`（目次の行の指紋）で配る。ブラウザは使う前に毎回 `If-None-Match` で「この指紋のままか」を聞き、同じなら `304`（本文なし。KV も読まない）、差し替えられていれば新しい中身を受け取る。以前は `max-age=3600` で、別の端末には上書き前の pptx が最長 1 時間残っていた（2026-10-21 に直した）。問い合わせが起きるのは「スライドを作ってダウンロード」（素材 1 本ごと）とマスタの「開く」だけ

### 2.6 変更の記録（`meta/changes/`）の読み方

正本を書き換えるたびに 1 件足す（`src/lib/api.mjs` の `recordChange`。2026-10-23 から。`docs/slides-role.md` §7）。
読むのは `GET api/changes?days=N`：今日から N 日分（既定 7、最大 92）を新しい順に返す。**日は UTC で数える**（日本時間の 9:00〜翌 8:59）。`days=1` は「直近 24 時間」ではない。担当者の窓口からは読めない。

| 項目 | 意味 |
|---|---|
| `at` | いつ（UTC。日本時間は +9 時間） |
| `who` | 誰が。受付の証明のメール。機械（サービストークン）と手元は `null` |
| `via` | どの入口から。`input-shuho`＝牧師の画面、`slides`＝担当者ページ、`local`＝手元、`wrangler`＝運用者が wrangler で正本に直接置いた（画面を通らないので、記録は手で足す。2026-10-24 のテンプレ一式 29 個の初回登録、置き場の移行 `scripts/migrate-files.mjs`） |
| `op` | `put`（書いた。新規と上書きを区別しない）／`delete`（消した）／`save`（週を保存）／`rename`（週の日付を変えた）／`migrate`（置き場の移行でファイルの目次の行を作った。`docs/file-store.md` §4） |
| `key` | どのデータか（D1 のキー。素材は `files/…`） |

| 画面の操作 | op・key | 追加の項目 |
|---|---|---|
| 讃頌歌・交読文の新規登録・題の変更 | `put` `masters/hymns.json`（`readings.json`） | `titles`：番号 → `[前の題, 後の題]`。**新規は前が `null`** |
| 同じく、マスタの削除 | `delete` 同上 | `titles`：**削除は後が `null`** |
| pptx の登録・差し替え／削除（「両方削除」は pptx → マスタの 2 件） | `put`／`delete` `files/hymns/<番号>.pptx` など | `size`（登録・差し替え） |
| テンプレ pptx・聖句の型の差し替え | `put` `files/template/…` | `size` |
| 「ファイルの差し替え」（JSON）・同期の「送る」 | `put` そのキー | `by: "replace"` |
| 紙面の位置の「編集」 | `put` `texts.json`（聖句・標語）／`prayer-list.json`／`church.json`（住所・連絡先・牧師連絡先） | — |
| 週の保存 | `save` `weeks/<日付>.json` | `pruned`：残す週数を超えて消えた週 |
| 週の日付の変更 | `rename` 元の週 | `to`：新しい週 |
| サイトに反映 | `put` `public/current.json` | `date`：反映した週 |

- **何から何に変わったかは、題（`titles`）のほかは記録に無い。** 前の中身は控え `history/<key>/<時刻>`（記録の `at` と同じか直前の時刻）にある。控えができるのは、マスタ・教会情報・祈り課題・据え置きの文・公開用が実際に変わったときと、ファイルを差し替え・削除したとき（ファイルの控えは目次の行 `history/index/<名前>.json/<時刻>`。指していた中身は KV の `blobs/` に残る）。**週の保存・日付の変更は控えを作らない**。**控えは 14 日で消える**（毎朝 3:00。`docs/file-store.md` §3）。
- 記録しないもの: 毎朝の片付け（結果は `meta/cleanup/last.json` と Workers Logs の `[片付け]`）、PDF の写しとエンジンの記録（`meta/` の内部のもの）。
- 題の前後を残す形（`titles`）にする前の記録は、触った番号だけ（`nos`）。本番の週報 Worker に記録が入ったのは 20:43（日本時間）で、それより前は 17:19 からのプレビュー版の牧師の画面の分しか無い。
- 日ごとの表を読んで足して書くので、同じ瞬間の 2 件は片方が落ち得る（週に数回なので許す）。

## 3. 週データ（`weeks/<日付>.json`）

### 3.1 形

`date`（日曜、`YYYY-MM-DD`）／`service_name`／`reception`／`morning`（主日礼拝）／`schedule`（聖歌隊・ワーシップ・青年会）／`sunday_school`（JJS）／`afternoon`（午後礼拝）／`next_week`（次週の奉仕予定）／`wednesday`（水曜祈祷会）／`announcements`（報告）／`last_week`（先週の出席・献金）／`slides`（説教中の引用聖句 `sermon_refs`）。

- 人物は `{id, display}`。`id` は名簿の id、`display` は**印刷する文字列**（肩書は時期によって変わるので、その週に印刷した形のまま残す）。名簿に無い人は「直接入力」（`id` なし）。
- 式順は `config.json` が標準。「式の編集」をした週だけ `<section>.program` が入り、以後その週はそれが正になる。
- 古い週にある `verses` は**読まない**（据え置きの文は `texts.json` に移した）。
- **題の改行位置**（2026-10-24）: 説教題・お話の題は、題の文字列（1 本のまま）と並べて `<題のキー>_break`（紙面で 2 行にするときの 1 行目の字数）を持つ。キーが無い・`null`・範囲外（1 未満、題の字数以上）は 1 行（キーが無いのは、この項目を足す前の週と、題の欄を触っていない週。どれも同じ意味なので、古い週を変換する処理は持たない）。対象は `morning`・`afternoon`・`wednesday` の `sermon_title`、`sunday_school.title`、`next_week.morning`・`next_week.afternoon` の `sermon_title`、`next_week.sunday_school`・`next_week.youth` の `title`。字数は文字単位（サロゲートペアも 1 字）。スライドとサイトは題の文字列だけを使う（改行位置は紙面の都合なので題に混ぜない）。紙面の描き方は §5.2。

### 3.2 識別子と版

- **識別子はキーの日付。** 中身の `date` はキーに合わせる（`readWeek`）。
- **版（version）＝保存してある本文の SHA-1 の先頭 12 桁**（`versionOf`）。開いたときの版を画面が覚えておき、保存のときに送る。

## 4. 画面の操作と、サーバーで起きること

### 4.1 前提（保存の考え方）

- **入力は画面のメモリにだけある。「保存」を押すまで、サーバーにも端末にも残らない。** 下書き・localStorage・自動保存は持たない（ユーザーの決定、docs/OPERATIONS.md「設計上の約束」）。
- タブを閉じる・再読み込みする・別の週に切り替えるときに保存していない変更があれば、ブラウザの確認が出る（`beforeunload`、`openWeek` の `confirm`）。ただし iPad・スマホでブラウザがタブを裏で捨てたときや、OS・ブラウザが落ちたときは**確認なしで消える**。

### 4.2 開いたとき（`init`）

1. ログインの確認（Google サインインが有効なときだけ。いまは無効で、Access が前にいる）
2. `api/bootstrap` で名簿・曲名・交読文・祈り課題・教会情報・据え置きの文・保存済みの週の一覧を読む（**一覧はこの時だけ読む**。別の端末で保存された週は、再読み込みするまで一覧に出ない）
3. `api/engine` で PDF エンジンの状態を見る。Render のときは返事が来るまで「準備中」（§14.1）。返事に `ready` が付く（Render の `/health` に失敗したら `false`）。`meta/cf-chromium.json` が 24 時間より古ければ更新する。以後、画面を開いている間は 10 分ごとに同じ確認をして Render を起こしておく
4. PDF の表示（PDF.js）の用意を始める（§5.1。失敗しても、表示するときにやり直す）
5. **いちばん新しい保存済みの週を自動で開く**
（以前の「新しい週」の日付欄は無くなった。作る日付の初期値＝次の日曜は、「新しい週を作る…」の窓を開いたときに入れる。§19）

### 4.3 ヘッダの操作

保存の状態はヘッダに常に出す: 「まだ保存していません」（新しい週）／「未保存の変更があります」／「保存しています…」／「保存済み 14:52」（今日以外は「9/14 22:38」。サーバーが最後に書いた時刻＝`api/week/:date` の `saved_at`、保存の応答の `x-saved-at`）。

ヘッダは 1 段（高さ 56px、折り返さない）: 左端に「週報｜マスタ」の切り替え（§14.8）、その右に**いま開いている週**（日付と号数。860px 未満では年と号数を省く。押すと週の操作の一覧）、右に保存の状態・「サイトに反映…」・**保存**・「…」（その他: フォント〈評価用〉、サイトに出ている週、システム〈PDF エンジンの版・今日の生成回数〉、ログイン中のアカウント）。
マスタを開いている間は、週・保存の状態・「サイトに反映…」・「保存」を出さない（§14.8）。デザインの案と選んだ理由は `docs/design/header-options.html`（ヘッダ）と `docs/design/master-place-options.html`（週報｜マスタ）。

### 4.4 保存（`POST api/save`）

1. 画面で必須欄を確かめる（空ならそのタブへ移動）
2. 送るもの: 週の全部・フォント・`base_version`（開いたときの版）
3. サーバー: いまの版と `base_version` を比べる。違えば **409**（「別の場所で保存されています」または「サーバー側の週が削除されています」）
4. 409 のとき、画面で `confirm`: **OK＝この画面の内容で上書き**（`force`）／キャンセル＝保存しない
5. サーバー: **先に PDF を作る**（写しがあれば使う）→ **PDF ができてから** `weeks/<日付>.json` を書く → `meta/pdf/<日付>.json` を書く → 保持の上限を超えた古い週を消す（§4.6）→ 返事: PDF 本体と `x-version`・`x-saved-at`・`x-overflow`・`x-pruned`（消した週）
6. 画面: 版を更新し、「保存しました」を出す。知らせには「PDF を保存」「控え（JSON）を保存」のボタンを付ける。保存した PDF はプレビュー欄に渡す（§5.1）。**保存ではダウンロードしない**（2026-10-23 から。§4.8）

**保存の成否は、サーバーの返事（5）だけで決める。** 返事が来た後の処理（PDF の本文の受け取り・プレビュー欄への表示）は後処理で、失敗しても「保存しました」は変えない。表示できなかった理由はプレビュー欄の中に出す（「もう一度表示」付き）。
2026-10-22 まではこの区別がなく、保存は成功していたのに、表示の失敗で「保存できませんでした。もう一度『保存』を押してください」と出ていた（§4.8）。

保存するのは**送った瞬間の内容**。保存中に入力した分は「未保存」のまま残り、知らせのボタンで渡す JSON も送った内容と同じ。待っている間は、画面上部に進み具合のバーと「閉じないでください」を出す（§14.3）。

**PDF が作れなければ、保存も失敗する**（週データは書かれない）。画面に「失敗: …」と出て、入力は画面に残る。このとき `meta/pdf-log` にも何も残らない（記録は PDF ができた後に書く）。

### 4.5 編集権（同じ週を 2 か所で開いたとき）

- **同じブラウザの中**（同じプロファイル）: Web Locks で、日付ごとに 1 タブだけが編集できる。**違う週なら、別々のタブで同時に編集できる。** 2 つ目のタブは開くと最新の週を開こうとするので、その週が編集中なら待機画面（「◯月◯日の週は、別のタブで編集中です」）になり、1 つ目を閉じると編集できるようになる。待っている間もヘッダの週の一覧は使え、別の週を選ぶと待ちは取り消される（2026-10-11 修正: それまでは一覧が待機画面の裏に隠れて選べず、選べても古い週の待ちが残って、相手が閉じた瞬間に読み込み直されていた）。
- **別の端末・別のブラウザ**: 止めるものはない。後から保存した方が 409 を受ける → 上書きを選ぶと、先に保存した内容は消える（履歴は残らない）。

### 4.6 保持（`RETAIN_WEEKS`、いま 5）

- 保存のたびに、保存済みの週を日付順に並べ、**新しい方から 5 週だけ残して古い週を消す**（`weeks/` と `meta/pdf/`）。
- 値の正本は `wrangler.jsonc` の `vars.RETAIN_WEEKS`。ダッシュボードで変えても次のデプロイで戻る。設定が抜けたときは `worker/index.mjs` の予備の 2（少ない側に倒す）。
- 経緯: 要件 v7 は「current と previous だけ置く。個人情報を溜めない」で 2。2026-10-23、保存時の自動ダウンロードをやめた（§4.8）ので控えが端末に残りにくくなり、ユーザーの判断で 5 に増やした。容量は無料枠のごく一部（週データは 1 週約 6 KB。D1 の上限は 1 データベース 500 MB。PDF の写しは KV に期限〈保存 90 日〉で残り、週数とは無関係）。
- **注意（落とし穴）:** 「いちばん古い日付」は、いま保存した週でもありうる。例: 10/4 と 10/11 がある状態で 9/27 を作って保存すると、保存は成功するが、**9/27 はその場で消える**。
- **消えることを知らせる**（2026-10-23 から。保存で控えが自動で残らなくなったため）:
  - 保存の返事の `x-pruned` に消した週が入る。画面は「◯/◯ の週はサーバーから消えました」を保存の知らせに足し、週の一覧から外す。
  - いま保存した週自身が消えたときは、赤い知らせで「サーバーからすぐに消えました。残すには、いま PDF と控え（JSON）を保存してください」と出し（ボタン付き）、その週は「まだ保存していません」に戻す（閉じると確認が出る）。
  - 「新しい週を作る…」の窓で、作る日付を保存すると消える週を先に知らせ、その週の「控え（JSON）を保存」をその場に出す。残す週数は `api/bootstrap` の `retain_weeks`（無制限なら `null`）。
- 過去の週を作り直すときは、牧師の手元の JSON を「JSON を読み込む…」で入れる。

### 4.8 iOS の Safari とダウンロード（2026-10-22 の事象から。2026-10-23 決定）

**事象**: 10/19・10/22、牧師が iPad（Safari 27.0.1）で保存すると「保存できませんでした（理由: Importing a module script failed.）」と出た。
Workers Logs では、iPad の保存 5 回はどれもサーバーで成功（200）していた。止まっていたのは、保存後に保存した PDF をプレビュー欄に描く段階で、Windows の保存・プレビューは毎回描き終わっていた。
10/22、ユーザーの iPhone（Safari 27.0.1）で再現した（10/18 の週を変更なしで保存）。

| 試したこと | 結果 |
|---|---|
| 開き直してすぐ保存（PDF.js を読んでいない） | 「Importing a module script failed.」。確認は JSON の 1 回だけ出て、**PDF のダウンロードは消えた** |
| プレビュータブ（ダウンロードなし） | PDF が出る（Safari 27 は PDF.js を読める） |
| プレビューの後に保存（PDF.js の本体は読み込み済み） | 「Setting up fake worker failed: "Importing a module script failed."」（今度は裏方＝worker の読み込みが落ちた） |

**iOS（iPhone・iPad）の Safari の特性**（WebKit Bug 220621「iOS: requests started during pending download are cancelled」、2021 年から未解決）:
1. ページがダウンロードを始めると「ダウンロードしますか？（表示／ダウンロード）」の確認が出る。**答えるまでの間にページが始めた通信は失敗する**（fetch も、モジュールの読み込みも、Web Worker の読み込みも）。
2. **確認が出ている間に次のダウンロードを始めると、先のダウンロードは消える**（確認は最後の 1 つだけ出る）。確認に答えたことを、ページから知る方法はない。
3. **PDF など Safari が自分で表示できる種類のファイルは、`download` 属性があっても、確認なしに同じタブで開く**（WebKit Bug 263608、2023 年から未解決）。入力画面から離れてしまい、端末にも保存されない。2026-10-23、save-1 の試し用の版で、保存の知らせとプレビュー欄の「PDF を保存」の両方で起きた。

3 への対処を決めるため、iPhone の Safari 27.0.1 で 5 通りを比べた（`diag-download` ブランチの確認ページ。本番には入れていない）:

| 渡し方 | 結果 |
|---|---|
| A. いまのやり方（種類 `application/pdf` のまま `download` 属性） | 確認なしに同じタブで開く |
| B. 種類を `application/octet-stream` に伏せて `download` 属性 | **確認が出て、名前どおり（`.pdf`）に保存される** |
| C. 名前付きの `File`（種類 `application/octet-stream`）を `download` 属性 | B と同じ |
| D. サーバーが `Content-Disposition: attachment` を付けて返す PDF へのリンク | 確認なしに同じタブで開く（サーバー側の指定も効かない） |
| E. 共有シート（`navigator.share`） | 「"ファイル"に保存」で保存場所を選んで保存できる |

**B を採る**（`src/ui/dom.mjs` の `download`。渡すファイルはどれも種類を伏せる）。
- C を採らない理由: 結果は B と同じで、違いは「ファイル名を `File` にも持たせる」ことだけ。保存される名前は `download` 属性で決まるので、名前を 2 か所に書くことになり、食い違う余地が増えるだけで得るものがない。B は受け取った PDF・JSON をそのまま包み直すだけで済む。
- E を採らない理由: PC（Windows の Edge・Chrome）ではファイルの共有シートがほとんど使えず、端末で操作が分かれる。保存場所を選べる利点はあるが、B でも iPhone の「ファイル」の「ダウンロード」に入る。
- D が効かなかったので、「サーバーから保存用として返す」方式は iOS の対策にならない。

もとの作りは、保存の後に「PDF をダウンロード → JSON をダウンロード → その直後に PDF.js を読み込んで表示」と続けていたので、1 で表示の通信が落ち、2 で PDF が消えた。
さらに、表示の失敗を保存の失敗として出していた（アプリ側の不具合。§4.4）。

**決めたこと（この特性を前提にした作り）**:
- **保存は保存だけ。** 保存ではダウンロードしない。PDF と控え（JSON）は、保存の知らせのボタン・週の一覧・プレビュー欄から、**利用者が押した 1 回につき 1 つ**渡す（`src/ui/dom.mjs` の `download`）。押した処理の中で、**ダウンロードの後に通信を始めない**（サーバーから受け取る分は、受け取ってから最後にダウンロードする）。**渡すファイルの種類は伏せる**（上の 3）。
- **保存の成否はサーバーの返事だけで決める**（§4.4）。
- **PDF の表示に通信を要らなくする**（§5.1）。PDF.js は画面を開いたときに 1 回だけ用意し、裏方は使い回す。
- **裏で行う通信の失敗を、そのまま「故障」にしない**。PDF エンジンの確認（§14.1）は、通信そのものの失敗なら状態を変えずに確かめ直す。
- **画面で起きたエラーは Worker のログに残す**（`[画面のエラー]`。§2.5）。今回は牧師のスクリーンショットが無いと理由が分からなかった。
- **手元で特性を真似る試験**: `scripts/e2e-ios-download.mjs`（開発サーバに対して流す。確認が出ている間の通信を失敗させ、続けたダウンロードは先のものを「消えた」と数え、種類を伏せていないダウンロードは「同じタブで開く」と数える）。もとの作りではテスト 1〜3 と同じ結果になることを確かめてある。

**選ばなかった案**:
- 自動のダウンロードを 2 つ、間を空けて続ける: 確認に答えたことをページから知れないので、何秒空けても確実にならない。
- PDF と JSON を 1 つにまとめる（zip）: iPad で PDF を開くのに一手間増える。PDF に JSON を埋め込む案は、PDF を人に渡すと印刷しない欄まで渡ってしまう。
- JSON だけ自動でダウンロードする: 控えは毎回残るが、iPad では保存のたびに確認が出て、確認の間に裏の通信が落ちる場面が残る。控えの役目は、サーバー側の保持（§4.6、未決）で補う方針にした。
- iPhone・iPad のときだけ動きを変える: 端末を見分けて動きを分けると、試す組み合わせが増え、端末によって控えの残り方が違ってしまう。

## 5. PDF

- **プレビューも保存も、サーバーで作った PDF。** ブラウザで紙面を描く方式は「二つの真実」になるのでやめた。表示は PDF.js（iPad の Safari・Android でも同じタブの中に出す）。
- **エンジン**: `PDF_ENGINE=render`（いま）→ Render Free のコンテナ（`scripts/pdf-server.mjs`、Chrome for Testing 128.0.6613.137）。15 分使わないと眠り、起きるのに 30〜60 秒かかる。入力画面を開いた時点で起こす。応答がなければエラーにする（Cloudflare に自動では切り替えない）。
  `cloudflare` → Browser Rendering。Free は「新しいブラウザ 3 回/分・同時 3・1 日 10 分」。使い終わったらすぐ閉じる。上限に当たれば理由を書いたエラーにする。
- **写し（KV `pdf/<指紋>`）**: 指紋 = SHA-256（描く側に渡す JSON をキー順固定で文字列化したもの | フォント | テンプレの版 | エンジン/Chromium の版）。描く側に渡す JSON は、その週の印刷に要る分だけに絞る（`renderData`）。同じ入力なら作らずに写しを返す。
  - 結果: 曲名を直すと、その番号を使う週だけ作り直しになる。名簿を変えても作り直しにはならない（印刷される文字は週データの `display`）。祈り課題・教会情報・据え置きの文・テンプレ・Chromium の版を変えると、全部の週が作り直しになる（開いたときに作る）。
  - 「成果物を保管しない」原則との関係: 写しは消えても困らない一時的なもの（正本の JSON から同じものが作れる）という整理。**ただし中身は個人情報を含む紙面そのもので、保存した週の分は 90 日残る。**
- **記録**: 生成・写しの利用のたびに `meta/pdf-log/<UTC日付>.json` に 1 行追記する。画面の「今日の PDF 生成 n 回」はこれを数えている（日付は UTC なので、日本時間の 0〜9 時の分は前の日に入る）。
- **溢れ**: 縮小の規則（`fit-policy.json`）を全部当てても収まらない欄は、PDF 上で赤枠になり、画面に一覧が出る（表示欄の上と保存の知らせ。欄の名前と直し方の言葉に直して出す: `src/ui/pdfview.mjs` の `overflowText`）。保存はできる。式順（主日・午後・水曜）は、2 行の題で下がった行が枠の下（主日は聖句の上）を越えたら赤枠（縮小の規則 `program`。縮めずに見るだけ）。

### 5.1 画面での表示（PDF.js。`src/ui/pdfview.mjs`）

- PDF.js は 2 つでできている: 表の担当 `vendor/pdfjs/pdf.min.mjs`（画面に描く）と、裏方 `vendor/pdfjs/pdf.worker.min.mjs`（PDF を読み解く Web Worker。重い処理で画面が固まらないよう、ページの裏で動かす）。
- **ページで 1 組だけ用意し、裏方は使い回す**（`preparePdfEngine`）。画面を開いたとき（`api/bootstrap` の直後）に用意を始める。
  何も指定しないと、PDF.js は文書を開くたびに裏方を作り直し、そのたびに裏方のファイル（1.3MB）を取りに行く。用意済みの裏方を `getDocument({ worker })` に渡すと、文書を閉じても裏方は止まらない。
  → プレビュー・保存の後の表示は**通信なしで終わる**（PDF を作るのはサーバー。表示は届いた PDF を読み解いて描くだけ）。iOS の特性（§4.4・§4.8）で表示が落ちる場面を無くすための作り。
- **用意に失敗したら、次に表示するときにやり直す。やり直しは URL を変える**（`?retry=n`）。ブラウザも PDF.js も、読み込みに失敗したモジュールをページの中で覚えていて、同じ URL では失敗を返し続けるため（PDF.js は本物の裏方が読めないと同じファイルを画面側で読み直す〈fake worker〉が、その失敗も覚える）。
  裏方が応答しなくなった（文書を開くのに 30 秒以上）ときも、作り直す。
- **表示欄が隠れている間は、受け取った PDF を持っておくだけ**。表示欄が見えたときに開いて描く。表示できなかったときは、表示欄の中に理由と「もう一度表示」を出す（保存・プレビューの知らせとは別。保存の結果は変えない）。
- 費用: 画面を開くたびに PDF.js を確かめる（初回は約 1.7MB、以後は「変わっていないか」の確認だけ）。裏方は画面を閉じるまで数 MB のメモリを使う。

### 5.2 文字組み（原本の Word に合わせるところ。2026-10-24）

原本の Word は、欄ごとに字間（文字間隔）を変えていた（7/19 の docx と、見本 2024/4〜2026/9 の 14 部で確認）。字間は 2 種類ある。

- **毎週同じ固定の字間**（祈り課題 −0.6pt、使徒信条 −0.3pt 前後、式順の右の列 −0.7pt、本日の予定、JJS など）
- **その週の文字を入れるために詰めた字間**（賛美の曲名・説教題で 0〜−1.4pt。週ごとに違う）→ 縮小の規則（`fit-policy.json` の横倍率）が代わりをしている

固定の字間のうち改行に効くのは、複数行の欄だけ。1 行の欄は、詰めなくても位置が少し変わるだけ（はみ出せば縮小の規則が効く）。複数行の欄は次のように合わせる。

- **覚えて祈りましょう**: 見出しと全項目に字間 −0.6pt（原本の `w:spacing -12`）。無いと 1 項目が約 3mm 長くなって改行が原本とずれ、行が増えた分だけ縮小で文字も小さくなる（10/25 の週で 5 番が「…牧／師」、9.5pt になった）。
- **使徒信条**: 改行位置を原本に固定する。`config.json` の `apostles_creed.lines` が 1 要素＝紙面の 1 行（本文 15 行。見本 14 部とも同じ改行）。原本は行ごとに −0.2〜−0.6pt を手で使い分けて両端をそろえていたので、1 つの字間の値では再現できない（一律 −0.3pt では 3 行目でずれる）。
  最後の行以外は両端揃え。IPA P明朝では 15 行のうち 3 行（「…ピラト」「…死にたる」「…からだのよ」）が欄より最大 1.6mm 長いので、その行だけ縮小の規則 `creed_line` の `squeeze`（はみ出した幅を字数で割って字間を詰める。約 −0.26pt）で 1 行に入れる。
  行数が決まっているので縦の縮小はしない（行送り 5.65mm、1 行目の基線は原本と同じ 116.7mm）。以前は 1 本の文字列を折り返していたため、5 行目で「ピラ／ト」と割れて 1 行増え、縦の縮小で行送りが 5.1mm に詰まっていた。

**題の 2 行**（改行位置のある題。§3.1。2026-10-24 ユーザー判断：見本 5 案から「9pt・行送り 3.5mm・2 行目をそろえる」を選んだ）
- 2 行とも 9pt。2 行目の頭を「の内側にそろえる（2 行目の前に見えない「を置く）。行の境目の空白は印字しない。
- 横に入らなければ、長い方の行に合わせて 2 行とも同じ倍率で縮める（縮小の規則 `title_2line`: 92→85→80%→8.5pt）。
- 式順（主日・午後・水曜）: 説教の行を 7.0mm（行送り 3.5mm × 2）にし、項目名と名前は 2 行の真ん中。下の行は下がり、エリアの下の余白で吸収する（10/24 実測の余白: 主日 15〜22mm、午後 8〜24mm、水曜 6〜13mm）。
- 次週・本日の JJS: 2 行目は次の行（行送りはその欄のまま）、項目名は 1 行目。本日の JJS・中高科は固定した枠の空き 1 行分を使い、行は上から。
- **題を入れてよい幅は 8 か所とも 33.1mm（125px）**（2026-10-24 ユーザー判断）。一番狭い次週欄・水曜の幅にそろえた。主日（欄は 37.6mm）・午後（35.4mm）・本日の JJS（33.9mm）でも、題はこの幅を超えたら縮める。欄の並び（項目名・題の欄・名前の欄の位置と幅）は変えず、縮小の判定だけこの幅で行う（`fit-policy.json` の `_title_width_px`、要素の `data-fit-width`）。短い題の見た目は変わらず、長い題は題の終わりから名前までの空きが広がる。同じ題が次週欄から翌週の主日・午後に写っても同じ見え方になり、入力画面の「入るか」も欄によらず同じになる。
- **題は自動では折り返さない**（2026-10-24。改行は人が決める）。1 行の題は 8 か所とも同じ縮め方（縮小の規則 `title`: 92→85→80%→9pt→8.5pt。それまで次週欄は 85% の次に自動で折り返し、本日の JJS は 9pt まで、と欄ごとに違った）。縮めても入らなければ赤枠と「2 行にしてください」の知らせ（知らせは欄の名前つき。例「次週の JJS の題（1 行に入りません。…）」）。それまで自動の折り返しで 2 行になっていた題は、改行位置を入れ直すまで赤枠になる。1 行に入る字数は、縮めずにひらがな 9 字・漢字 8 字、一番縮めてひらがな 14 字・漢字 12 字まで（「」を除く）。
- 次週欄の行送りは初めから 3.6mm（それまでどの週も 3.9 → 3.6mm に詰まっていた）。足りなければ、区切りの空き（各 1mm まで）→ 行送りの順に詰める（`nextweek_body`）。小見出しの間を先に詰めるので、行の間隔はなるべく保たれる。

**真ん中の列の枠（本日の予定・JJS・中高科・使徒信条）は、どの週も同じ位置・大きさ**（2026-10-24 ユーザー判断。原本の配置から変えた）。
- 位置は下から決める（10/24 ユーザー指示）。**使徒信条の上端は水曜祈祷会の上端（107.23mm）にそろえる**（下端は原本の 202.52mm。行送り 5.65mm・改行とも原本のまま、1 行目の基線 116.7mm・アーメン 201.4mm も原本と同じ）。
- JJS（61.48〜85.54mm）と中高科（86.90〜106.47mm）の枠は、お話の題が 2 行のときの大きさ（原本より 1 行分＝3.9mm ずつ大きい）に固定。題が 1 行の週は、空く 1 行分を行の上下に半分ずつ置く（行を枠の上下の真ん中に）。
- 残りを本日の予定（10.34〜60.30mm）に回す。行の下に約 9.3mm の余白が残る（原本はここが仕切りの線で区切った空欄 12.11mm で、見本 14 部とも毎週空だった。仕切りの線は引かない）。
- 枠と枠の間（1.18・1.36・0.76mm）は原本のまま。題が 2 行の週に枠を動かす作りにしなかったのは、週によって枠が動かない方が紙面が安定し、作りも簡単なため（見本で 3 案と比べて決めた）。

## 6. 認証と公開範囲

| 層 | いま（リハーサル） | 本番の予定 |
|---|---|---|
| Worker の前 | **Cloudflare Access**（Worker 単位）。人＝メール一覧とワンタイム PIN、機械＝サービストークン | 同じ（Worker 単位の Access はカードなしで使える。`docs/slides-role.md` §8・§9） |
| API の門番（`src/lib/auth.mjs` の `accessGate`、2026-10-23） | **受付の証明（`Cf-Access-Jwt-Assertion`）が無い API は 403**。人でも機械でも、この受付の正しい証明なら通す | 同じ |
| アプリのログイン（`src/lib/auth.mjs` の `withAuth`） | **無効**（`GOOGLE_CLIENT_ID` が空） | 未決。門番は受付を前提にしているので、Google サインインに切り替えるなら門番を見直す |
| 歌詞・聖書の API | 受付の証明があれば開く（ほかの API と同じ） | 同じ |
| 受付が外れても読めるもの | `api/public/current`（サイトのビルドが読む。公開してよい情報）と、静的アセット（画面の HTML・JS・CSS、`/shuho-assets/` のテンプレ・フォント）。**どれもデータは入っていない**（§10 の 7） | 同じ |

- **データは `api/` からだけ渡す**（§10 の 7）。静的アセットは Worker のコードを通らずに Cloudflare が返すので、門番が効かない。だから静的アセットにはデータを入れない。`tests/assets-no-data.test.mjs` が、実際に組み立てた `dist/`・`dist-slides/` で確かめる（置いてよいファイルの一覧と、名簿・教会情報・祈り課題・据え置きの文の値が入っていないこと）。
- **門番は、受付を外したときに「誰でも入れる」ではなく「誰も入れない」で止めるためのもの**（`docs/slides-role.md` §6 の 2）。受付が外れる場面: 教会のアカウントに移した直後（新しい Worker には受付が無い）、ホームページを公開するときの取り違え、調査で一時的に外して戻し忘れ、など。**門番が防げないこと**: 名簿（ポリシー）に誰でも入れる条件（「Everyone」など）を書いたとき。受付が誰にでも正しい証明を出すので、門番は通してしまう。名簿は牧師用（`shuho-editors`）を他と共用しない。
- 門番の例外: `public/` の GET と、手元（`wrangler dev`、宛先が localhost）。Cloudflare を通る要求の宛先が localhost になることはない。
- **受付を作り直すと AUD が変わり、`ACCESS_AUD` を直すまで API は全部 403**（牧師も入れない）。断った理由は返事の `reason` と Workers Logs（`[受付なし]`）に出る。アカウントを移すときは `ACCESS_TEAM_DOMAIN` も直す。
- 門番が効くのは門番を入れた版（2026-10-23 以降）だけ。過去の版ごとのプレビュー URL（§13）は古いコードのまま動くので、受付が外れるとそこは開く。
- **担当者用 Worker**（§20）: 受付は名簿 `shuho-slides`（ほかに開発者の `Cloudflare account members` と、開発の確認用のサービストークン `claude-dev-auth`。2026-10-29 に Access の API で確かめた）。コードも受付の証明を確かめ、**人（メール）の証明が無ければ断る**（機械の証明も通さない）。週報 Worker へは内線で渡し、内線は受付を通らないので、窓口 `SlidesWindow` の許可の一覧がそのまま担当者の権限になる。

- **受付のログインが切れたまま API を呼ぶと**、要求は受付で止められる。入力画面の扱いは §6.1。
- **誰が保存したかは `meta/changes/` に残る**（2026-10-23 から。受付の証明のメール）。それより前の保存は時刻しか残っていない。
- 個人情報（会員名・出席・献金額）を Cloudflare に置くには小会の承認が要る。**ログインを入れるまで実データは置かない**という方針。リハーサルでは、名簿・祈り課題・連絡先・週データは仮名化したものを使っている（曲名と交読文は実物）。

### 6.1 受付のログインの期限切れ（2026-10-24）

- **受付（Access）のログインは、ワンタイム PIN を入れた時から決まった時間で切れる。使っても、読み込み直しても延びない。** いまは 24 時間（Zero Trust のアプリ「samplechurch-shuho - Cloudflare Workers」のセッションの長さ）。Cloudflare には「使うたびに延長」の設定が無い（文書「Session management」。長さを決められるのは、全体のセッション〈チームのドメイン、15 分〜1 か月、既定 24 時間〉と、アプリ・ポリシーのセッション〈すぐ〜1 か月〉だけ）。アプリの印が切れても全体のセッションが生きていれば、ページを開き直すだけで PIN なしで印を出し直す。いまはどちらも 24 時間で同時に切れるので、切れたら PIN が要る。
- 切れた後も、開いている画面はそのまま動く（入力は画面のメモリにあり、入力の間は通信しない）。気づくのは次の通信のとき。
- 切れた後の要求: 受付は `X-Requested-With: XMLHttpRequest` が付いていれば **401**（`www-authenticate: Cloudflare-Access …`）、付いていなければ受付のログイン画面（別のドメイン）へ **302**。後者は fetch が追って CORS で失敗し、画面からは「通信の失敗」にしか見えない（2026-10-24 に本番の受付で確かめた）。**受付で止められた要求は Worker に届かない**ので、Workers Logs にも画面のエラーの記録（`[画面のエラー]`）にも残らない。
- 入力画面（`src/ui/dom.mjs` の `guardLogin`）: 同じ場所への fetch すべてに `X-Requested-With` を付け、受付の 401 を `LoginExpired` にする。
  - 知らせ（閉じるまで残る）:「ログインの期限が切れました。保存していない入力は、この画面に残っています。この画面は閉じたり読み込み直したりせずに、『ログインし直す』を押してください。開いたタブでログインしたら、この画面に戻って続けてください」。PDF の準備の知らせは消す（食い違うので）。エンジンを「失敗」にはしない
  - 「ログインし直す」は、新しいタブで `relogin.html` を開く → 受付のログイン画面 → PIN → `relogin.html`（「ログインできました」）。`relogin.html` は BroadcastChannel で元の画面に知らせ、自分を閉じる。受付の印は同じホストのタブで共通なので、元の画面の通信も通るようになる。**元の画面は読み込み直さないので、入力は残る**
  - 元の画面は、知らせを受けたとき・前に出たとき・保存やプレビューを押したときに確かめ直し（`api/auth/config`）、通れば知らせを消して「もう一度『保存』を押してください」を出す（棄却した操作があるとき。§14.2 と同じく、自動では続けない）
  - 保存の要求そのものが止められたときも同じ扱い（サーバーには届いていない）。ほかの操作の失敗の文は「ログインの期限が切れました（『ログインし直す』を押してください）」
- 試験: `scripts/e2e-engine-login.mjs`（受付の返事の形を真似る。`login-save`・`login-direct`）。iPad の Safari の実機ではまだ確かめていない。
- **担当者ページはまだこの扱いが無い**（切れると「通信できませんでした（インターネットの接続か、ログインの期限切れの可能性があります）」）。
- 防げないこと: 元の画面を読み込み直したとき（受付のログイン画面になり、入力は消える）。iPad の Safari が裏のタブを捨てたとき（R1）。
- 運用: 作業を始めるときは読み込み直す（切れていれば先に PIN を聞かれる）。ただし読み込み直しても期限は延びないので、ログインから 24 時間の境目の前後で作業すると、途中で切れることはある（そのときは上の知らせ）。

## 10. 変えない原則

1. **支払い方法（カード）はどのサービスにも登録しない。** 最悪の事態が「止まる」で済み、「請求される」が仕組みの上で起きないようにする（毎月確認する責任を教会に負わせない）。Workers Paid も提案しない。
2. **Git にはコードだけ。** 個人情報と運用データは Git に入れない。
3. **成果物（PDF・pptx）は保管しない。** JSON から作り直せる（KV の写しは一時的なもの、§5）。
4. **見たものがそのまま出る。** テンプレは 1 本、プレビューは実際の PDF。
5. **正本は Cloudflare（D1・KV）。** 手元・教会 PC・牧師のダウンロードは写し。
6. **下書きは持たない。** 保存するまで残らない（→ §12 で見直しの論点あり）。
7. **データは `api/` からだけ渡す。** 静的アセット（画面の HTML・JS・CSS、紙面の型・フォント）にはデータ（名簿・週・マスタ・教会情報など）を入れない。注釈の例にも実在の名前を書かない。静的アセットは門番（受付の証明）を通らずに返るため（§6）。`tests/assets-no-data.test.mjs` で確かめる（2026-10-23）。

## 14. 入力画面の作り（UI の仕様）

2026-10-11 決定。改修はブランチ `ui-1` でコミットを分けて進め、deploy はユーザーの確認後にまとめて行う。

### 14.1 PDF エンジンの準備（Render のとき）

画面は PDF エンジンの状態を 3 つで持つ: **準備中／準備完了／失敗**。Cloudflare・ローカルのエンジンは眠らないので、常に準備完了。

- **確かめ方**: `api/engine` を 1 回送り、返事を待つ（Worker が Render の `/health` を呼ぶ。`/health` は Chromium の起動まで済ませてから返す）。本番 Cloudflare の Chromium の版の確かめ直し（ブラウザを起こすので数秒〜失敗があり得る）は `api/engine/production` に分け、画面が裏で呼ぶ。`api/engine` は覚えている版を返すだけで、準備完了をそれに巻き込まない。繰り返し問い合わせることはしない。眠っている間は、問い合わせても起きるまで保留されるだけなので意味がない。
  **返事が来た＝準備完了。** 時間で「眠っている／起きている」を判定することはしない。
- **いつ確かめるか**: 画面を開いたとき。画面を開いている間は 10 分ごと（Render は 15 分で眠るため、起こしておく）。画面が裏から戻ったとき（iPad はタブが裏に回るとタイマーが止まる）。最後の返事から 14 分以上たってプレビュー・保存を押したとき。
- **進み具合**: Render から起動の進み具合は取れない。**平均時間を目安にバーを進め、終わる手前で止めて待つ。返事が来たら完了にする。** 1 秒以内に返事が来たらバーは出さない（ちらつき防止。判定ではない）。
  平均時間は Worker が実測して記録する（起動に 10 秒以上かかった回だけ、直近 20 回。`meta/render-wake.json`）。記録が無いうちは 50 秒。
- **バーの置き場所**: プレビュータブの中（画面の右端）に小さく。
- **失敗**: Worker 側で 75 秒たっても返事が無ければ失敗。タブに「PDF の準備ができませんでした（押すとやり直し）」を出す。通信の失敗が続いて失敗にしたときは「通信できません（押すとやり直し）」（エンジンのせいにしない。2026-10-24〜）。
- **通信そのものの失敗は、すぐには失敗にしない**（2026-10-23〜）。電波が切れた・iOS のダウンロードの確認中だった（§4.8）などで `api/engine` が届かなかったときは、状態を変えずに 3 秒・6 秒・9 秒後に確かめ直し、続けて 4 回届かなければ失敗にする。準備完了のままなら、その間もプレビュー・保存は使える。

### 14.2 準備中の操作は棄却する

プレビュー・保存とも、**準備完了のときだけ動く。** 準備中・失敗のときに押された操作は、**待たせずに棄却し、理由を知らせる。** 準備が終わっても自動では続けない（もう一度押してもらう）。

- 理由: 押した操作が準備の完了に依存しないようにする。待たせて後で続ける方式だと、待つ間の入力・週の切り替え・二度押し・準備の失敗をすべて扱う必要が出る。
- プレビュータブ: 灰色にする。押されたら「プレビューしていません。PDF の準備中です（ふだん約 n 秒）。準備ができたら、ここでお知らせします。そのあと、もう一度『プレビュー』を押してください」を出す。タブは切り替わらない。知らせの文は出したまま変わらないので、残りの秒数は書かない（進み具合はタブの横のバー）。
- 保存: 棄却したことを、**閉じるまで残る知らせ**で出す（文はプレビューと同じ形）。「未保存の変更あり」の表示は残る（§14.4）。
- **棄却した操作の知らせは、準備の結果で置き換える。** できたら「PDF の準備ができました。もう一度『保存』を押してください」、できなかったら「保存していません。PDF の準備ができませんでした（PDF エンジンが応答しません）／通信できません（インターネットの接続を確かめてください）。入力は画面に残っています。この画面を閉じずに、…もう一度『保存』を押してください」。2026-10-24 までは、できなかったときに置き換えず、「準備中です（あと約 23 秒）」とタブの「準備できませんでした」が並んでいた（§12 の既知の事象）。

### 14.3 PDF を作っている間の進み具合

- プレビュー・保存のどちらも、**ふだんの所要時間を目安にバーを進め、終わる手前で止めて待つ。返事が来たら完了にする。** 経過秒数も出す。
  目安は、直近の生成時間の平均（写しを使わなかった回、直近 20 回。`meta/pdf-durations.json`）。記録が無いうちは 12 秒。
- プレビュー: プレビューの枠に大きく出す。
- 保存: どのタブにいても見えるように出し、「閉じないでください」と添える。
- 保存中の入力: 保存するのは、送った瞬間の内容。保存中に入力した分は「未保存」のまま残る。

### 14.4 状態の表示とメッセージ

- 画面に常に出しておく状態（ヘッダ）: どの週を開いているか／保存の状態（まだ保存していません・未保存の変更があります・保存しています…・保存済み 14:52）。§4.3
- ヘッダは 1 段・高さ固定。案 A（週が主役）を採用（`docs/design/header-options.html`）。左端に「週報｜マスタ」（§14.8）。
- メッセージの出し方（`src/ui/dom.mjs` の `notify` / `inlineMsg`）:

| 種類 | 出し方 | 例 |
|---|---|---|
| **結果** | ヘッダの下の帯。**閉じるまで残る**。同じ種類は 1 つに置き換える（保存・週・日付・読み込み・プレビュー・反映・エンジン・ログイン・書き出し）。別の週を開くと前の週の知らせは片付ける。帯の中にボタンを置ける | 保存しました（「PDF を保存」「控え（JSON）を保存」付き。消えた週があれば足す）／保存できませんでした（入力は画面に残っています…）／保存していません（必須の欄が空・準備中・別の場所で保存されている）／日付を変更しました／JSON を読み込みました（保存すると上書き）／サイトを作り直しています → 反映しました／PDF・控えを用意しています |
| **表示の失敗** | プレビュー欄の中（§5.1） | PDF を画面に表示できませんでした（理由）。保存や「PDF を保存」には影響しません［もう一度表示］ |
| **入力の誤り・小さな結果** | その場所の横に 1 行 | 書名が一覧にない／新しい週の日付が日曜でない・既にある／讃頌歌・交読文の登録・更新・削除／据え置きのデータを保存しました／スライドを作っています |
| **進み具合** | バー（§14.1・§14.3） | PDF を作っています・保存しています・PDF の準備中 |
| **報告だけ** | 出さない | 読み込みました／新しく作りました／プレビューを更新しました／フォントを変えました |
| **開発者向け** | 「…」の中の「システム」、またはブラウザのコンソール | エンジンの版・生成回数・Web Locks が無い |

- 失敗の理由は牧師に読める文にする（`why`）: 通信の失敗は「通信できませんでした（インターネットの接続か、ログインの期限切れの可能性があります）」、画面の部品（モジュール）の読み込みの失敗は「画面の部品を読み込めませんでした（通信が途中で切れた可能性があります）」、ログイン画面への回り込みなどで JSON が読めないときは「サーバーから思わぬ返事が来ました」。

### 14.6 讃頌歌・交読文のマスタと pptx（2026-10-21、requirements-todo.md 項目 10）

- 番号ごとの状態は 3 通り: **完備**（マスタも pptx もある）／**pptx 未登録**（マスタだけ。黄色のバッジ）／**マスタ未登録**（pptx だけ。灰色のバッジ）。マスタは D1 の `masters/hymns.json`・`masters/readings.json`、pptx の有無は D1 のファイルの目次 `index/hymns/…`（`api/bootstrap` の `files`）で見る。

- 一覧は高さ固定（画面の 40%）でスクロールする。行を押すと、下のパネルにその番号のマスタと pptx（枚数・比率・更新日・元のファイル名、「開く」でダウンロード）が出る。
- **新規**（上の段）: 番号と題でマスタに登録する。既にある番号は上書きせず「既にあります」と出してその行を選ぶ。
- **題を更新**（パネル）: 題を変えたときだけ押せる。上書きで、前の題は `history/` と変更の記録（`titles`）に残る（2026-10-23〜）。番号は変えられない（変えるときは削除＋新規）。
- **pptx のアップロード**（パネル）: マスタにある番号だけ。マスタ未登録の行では「先にマスタに登録してください」と出し、上の新規欄に番号を入れる。ファイルを選ぶと「ファイルの差し替え」と同じ検査をし、16:9 でない・ファイル名の番号と違うときは注意を出す（止めはしない）。ボタンの名前で新規（「新規アップロード」）と上書き（「上書きアップロード」）を分ける。上書きの前の内容は KV の `history/` に残る。
- **削除は 3 通り**（パネル）: 「マスタだけ削除」（pptx は残り、マスタ未登録になる）／「pptx だけ削除」（pptx 未登録になる。前の版は控えに 14 日残る）／「両方削除」（pptx → マスタの順に消す。途中で止まっても pptx 未登録になるだけ）。使っている週があるかは見ない。
- **削除のロック**: 削除ボタンは、ふだんはグレーアウト。上の段の「削除を有効にする」を押すと、そのとき在るものに応じて押せるようになり（マスタだけ削除＝マスタあり、pptx だけ削除＝pptx あり、両方削除＝両方あり）、一覧とパネルの枠が赤くなる。「削除を無効に戻す」か、マスタを離れる（「週報」に切り替える）と戻る。
- **スライドタブ**: 主日礼拝・午後礼拝・水曜祈祷会のエリアの「スライドを作ってダウンロード」の上に、そのエリアで歌詞・交読文を入れる番号のうち pptx が無いものを赤字で出す（例「讃頌歌 6（賛美 1）の pptx が未登録です」。主日＝賛美 1〜3・交読文、午後＝賛美、水曜＝賛美 1・2）。タブを開いたとき・週を開いたとき・マスタで変えたときに数え直す。作ることは止めない。

### 14.7 題の欄（2 行にできる。2026-10-24）

対象は 8 か所: 主日・午後・水曜の説教題（式順の中）、本日の JJS のお話（中高科の欄にも写る）、次週の主日・午後の説教題、次週の JJS・中高科のお話しの題（`data-lines="2"` の欄。`src/admin/admin.js` の `titleLines`）。

- 普段は 1 つの欄。右の「2 行」で、1 行目・2 行目の 2 つの欄（紙面と同じく上下）に分かれる。「1 行に」で 1 つに戻す（題はつないだまま、改行位置は空）。
- 分ける位置: 最後にカーソルがあった位置。無ければ最初の空白の後、それも無ければ真ん中。分けた後は、それぞれの欄を直せばよい。
- 保存するのは、題（1 行目と 2 行目をそのままつないだ文字列）と改行位置（1 行目の字数。2 行目が空なら空）。1 つの欄に戻して打ち直すと改行位置は空。上限（説教題 40 字）は 2 つの欄を合わせた字数。
- 週を開いたとき、改行位置が使える題は 2 つの欄で出す。本日の中高科の欄（読むだけ）も 2 行で出す。
- 休止中の欄では、ボタンと 2 つの欄も触れない（ほかの欄と同じ）。
- **紙面の欄に入るか**を欄の下に出す（`src/ui/titlefit.mjs`）。そのまま入るときは何も出さない。縮めて入るときは「9pt・横 92% に縮めて入ります。」、入らないときは赤で「1 行に入りません。「2 行」にしてください。」（2 行なら「2 行でも入りません。題を短くするか、改行の位置を変えてください。」）。紙面のフォントにない字があれば、それも出す。字数の目安（「17字（目安15字）」）は題の欄では出さない。
  - 計算は紙面と同じ縮小の手順（`fit-policy.json`。1 行は `title`、2 行は `title_2line` で 9pt から）を、フォントの字幅表で当てる。このフォントは字の間を詰める情報を持たないので、字幅の足し算で PDF と同じ結果になる（10/24、本番と同じ Chrome 128 で描いた 24 欄と照らして全部一致）。
  - 題を入れてよい幅は `fit-policy.json` の `_title_width_px`（8 か所とも同じ。紙面の判定と同じ値）と縮小の規則（`title`・`title_2line`）を、`api/bootstrap` の `fit` で画面に渡す。この幅が 8 か所の題の欄の一番狭い幅と同じこと（どの欄にも収まること）は `tests/title-fields.test.mjs`（手元の Chromium で紙面を組んで測る）で確かめる。
  - 字幅表 `src/ui/glyph-widths.json`（約 22KB。1 字分でない字 847 と、フォントにある字の表）は `node scripts/glyph-widths.mjs` で作って Git に置く。フォントと一致することは `tests/glyph-widths.test.mjs` で確かめる（計画では組み立てのときに作るとしていたが、手元の開発サーバと Worker で同じファイルを配るだけにした）。
- デザインは 3 案（A: ボタンで上下の 2 つの欄／B: チェックで横に並ぶ 2 つの欄／C: 1 つの欄のまま「ここで改行」）から A を選んだ。B は次週欄の狭い幅で窮屈、C は改行の位置が欄に見えず、題を直したときに位置がずれる。

### 16.4 午後礼拝の案内（2026-10-11 決定）

- 「案内:」は**ふだん出さない**（入力画面にも紙面にも）。入力画面の「案内を追加」で、見出しの 3 行目に「案内：」と担当者の欄が出る。「外す」で消す（担当者も消す）。
- 紙面: **担当者が入っている週だけ** 3 行目「案内：担当者」を印刷し、式順を 1 行分（5.7mm）下げる。担当者が空なら印刷しない。ワーシップ曲 4 曲までなら枠に収まる（約 87.7mm／91.8mm）。
- 週データ: `afternoon.usher`（担当者）、`afternoon.usher_shown`（入力画面で追加した印）。担当者が入っている週は追加済みとして開く。次の週には引き継がない（毎週、非表示から）。

## 17. 聖書箇所の入力（2026-10-16 決定）

入力欄（`src/admin/admin.js` の `refWidget`。招詞・聖書朗読・次週の聖書・JJS・引用聖句など全部共通）は、書名を一覧から選び、章・節をプルダウンで選ぶ。

- **節の初期値は空白（未選択）**。書名や章を選び直すと未選択に戻る。選択肢は「（空白）／章全体（詩篇は篇全体）／1〜n」。
- 保存される文字列:

| 選び方 | 保存される文字列 | 紙面 |
|---|---|---|
| 節が未選択 | `マタイ28:` | そのまま「マタイ28:」（節の入れ忘れが目で分かる） |
| 章全体を選ぶ | `マタイ28章` / `詩篇90篇` | そのまま |
| 節を選ぶ | `マタイ28:16` / `マタイ28:16-20` / `エステル5:1-8:17` | そのまま |

- **未選択でも保存できる**（入力の誤りとして止めない）。
- 開き直したとき: 節が無く、末尾が「章」「篇」なら章全体、そうでなければ未選択として表示する。
- **スライド（pptx）では、未選択も章全体と同じに扱う**（`src/lib/bible.mjs` の `parseRef` は「マタイ28」「マタイ28:」「マタイ28章」をすべて 28 章全体と読む）。未選択のままスライドを作ると、その章の全節のスライドが入る（2026-10-16 ユーザー判断で、いったんこのまま）。
- 変える前の点検（2026-10-16）: 手元の週データ 35 件の聖書箇所のうち、節なしは「詩篇◯篇」の 3 件だけで、すべて「篇」付き（章全体として正しく開ける）。本番のデータ（10/11・10/18 の 2 件）は 2026-10-18 に点検し、節なしの聖書箇所は 0 件だった。

## 18. 礼拝スライド（pptx）のエリア分け（2026-10-16 決定。2026-10-25 生成を作り直し）

スライドタブを 4 つのエリアに分け、それぞれに引用聖句の入力（1 行 1 箇所、追加・並べ替え・削除）と「スライドを作ってダウンロード」を置く。
休止・休みの週でも、入力・作成ともにできる。作るのはブラウザの中（`src/lib/slides/`、JSZip。Worker の CPU 制限のため）。
**生成の仕組みは `docs/pptx-template.md`**（背景スライド＋部品＋礼拝ごとの式順。目印 `{{…}}` と値の表、確かめ）。

| エリア | 引用聖句の保存先（週データ） | 並び（テンプレの式順） | ファイル名 |
|---|---|---|---|
| 主日礼拝 | `slides.sermon_refs`（これまでの「説教中の引用聖句」） | `template/式順/worship.json` | `<日付>.pptx` |
| 午後礼拝 | `slides.afternoon_refs` | `template/式順/afternoon.json` | `<日付>-午後礼拝.pptx` |
| 水曜祈祷会 | `slides.wednesday_refs` | `template/式順/wednesday.json` | `<水曜の日付>-水曜祈祷会.pptx` |
| その他 | `slides.other_refs` | `template/式順/other.json` | `<日付>-その他.pptx` |

- テンプレ一式（背景.pptx・背景.json・部品・式順）はマスタの「テンプレ」で直す（§14.9）。テンプレが約束どおりでないとき（部品が無い、曲・聖句の値がその礼拝に無い、色コードが違う など）は作らず、理由（どのファイルの何行目か）をエリアの注意の欄に出す。
- 歌詞ファイル・交読文ファイル・聖句が見つからないものは飛ばして注意を出す。作るスライドが 1 枚も無ければ作らずに知らせる。pptx が無い番号は、作る前にもエリアに出す（§14.6。準備賛美・賛美・交読文・聖餐式）。
- **準備賛美（2026-10-24）**: 主日礼拝のエリアの「準備賛美 [番号]」に、作る直前に入れる（ふつうは担当者）。番号は**週データに保存しない**。週報に印字されない値で使うのはスライドを作るその 1 回だけ、保存すると担当者に週データの書き込み口を開けることになるため（§20 の線を崩さない）。番号は画面を開いている間だけ残り、別の週を開くと空になる。空なら題のスライドを空欄で残し、歌詞は入れない。
- **聖餐式**: 週の式順（`morning.program`）に聖餐式があれば、主日礼拝の式順の「聖餐式」の行に、その番号の曲と歌詞が入る。無い週はその行ごと出ない（2026-10-24 までは入らなかった）。
- 担当者ページの「スライド」タブでも 4 エリアとも作れる（引用聖句は見るだけ。§20）。牧師の画面でも担当者ページでも、作る直前に週・マスタ・名簿をサーバーから読み直す（`src/ui/slide-maker.mjs`）。

## 19. 週を作る（2026-10-17 決定）

入口は 1 つ。ヘッダの週の一覧の「**新しい週を作る…**」で窓を開く（以前の「日付＋作る」の行を置き換えた）。

| 部品 | 中身 | 初期値 |
|---|---|---|
| もとにする週（X） | 保存済みの週から選ぶ。写すのは**サーバーに保存されている内容** | 今開いている週（一度も保存していない週なら、一番新しい保存済みの週） |
| 作る日付（Y） | 日曜だけ | 今日から見た次の日曜（今日が日曜なら 7 日後） |
| 写し方 | ① 新しい週として（毎週変わる欄は空）／② 丸ごと複製 | ① |

- Y がすでに保存されていれば作らない。
- 今の画面に保存していない変更があれば、「作る」のときに確認する（保存していない変更は写されず、破棄される）。
- 作った週は未保存の状態で開く。
- X の次週欄の休止が Y 当日に入るのは、Y が X の翌週のときだけ（§3.3「休止の写し方」）。
- 組み立てはサーバー（`api.mjs` の `week/<Y>/new?from=<X>&mode=fresh|copy` → `week.mjs` の `newWeekFrom` / `copyWeekFrom`）。`from` を省くと、Y より前で一番新しい保存済みの週（以前の動き）。

## 20. pptx 担当者ページと担当者用 Worker（2026-10-23）

設計と判断の経緯は `docs/slides-role.md`。ここは仕組みの要約。

**目的**: 週報に印刷される内容（週データ）の編集を牧師だけにしたまま、pptx 担当者（4 名、当番制、Google アカウントなし）がスライドとマスタの仕事をできるようにする。

| できること | 牧師の画面 | 担当者ページ |
|---|---|---|
| 週データの入力・保存・新規・日付の変更、サイトへの反映、同期、紙面の位置の「編集」 | ○ | × |
| 引用聖句 | 入力 | 見るだけ |
| スライドを作ってダウンロード（4 エリア） | ○ | ○ |
| 讃頌歌・交読文のマスタと pptx、テンプレ（背景と色・式順・部品。§14.9）、ファイルの差し替え（名簿・曲名・交読文の題・教会情報・祈り課題・据え置きの文）、マスタ一式のダウンロード | ○ | ○ |
| 保存済みの週の PDF を見る | ○ | ○ |

**権限の線を引く場所**（コードに「この人は牧師か」の判定は無い）
- 担当者が牧師の画面に入れない: 週報 Worker の受付の名簿（`shuho-editors`）に担当者がいない。
- 担当者が週データを書けない: 窓口 `SlidesWindow` の**許可の一覧**（`src/lib/slides-window.mjs` の `SLIDES_ALLOWED`）に、週の保存などの仕事が無い。許可の一覧なので、牧師の画面に API が増えても担当者には開かない。週データを書く仕事が無いことは試験で確かめる（`tests/slides-window.test.mjs`）。

**要求の流れ**
1. 担当者のブラウザ → 受付（名簿 `shuho-slides`）→ 担当者用 Worker。`slides/worker.mjs` が受付の証明（`Cf-Access-Jwt-Assertion`）でメールを確かめる。人でなければ 403（静的アセット付きの Worker には `ctx.access` が渡らないので、自分で確かめる）。
2. `slides/relay.mjs` が `/input-shuho/slides/api/<仕事>` を、誰からか（ヘッダ `x-shuho-actor`。ページから同じ名前で送られても上書き）を付けて内線へ渡す。**どの仕事を通すかは中継では選ばない**（許可の一覧は窓口の 1 か所だけ）。
3. 週報 Worker の `SlidesWindow`: 誰からかが無ければ 401、許可の一覧に無ければ 403（画面には「この操作は担当者ページではできません」）。通れば URL を `SHUHO_PUBLIC_ORIGIN` の `/input-shuho/api/<仕事>` に書き換え、牧師の画面と同じ API（`makeApi`）に渡す。
- `api/whoami`（見出しの「ログイン中」）と `api/client-log`（画面のエラー。担当者用 Worker の Logs に誰からか付きで残す）は、担当者用 Worker が自分で答える。

**画面**（`src/slides-page/`。見た目は `src/admin/admin.css`）: 見出しに「週報｜マスタ」（牧師の画面と同じ部品 `src/ui/place.mjs`。§14.8）、週の選択（保存済みの週から選ぶだけ。マスタの間は出さない）と「ログイン中」。週報の側のタブは「スライド」「週報（PDF）」。マスタと pptx・ファイルの差し替え・PDF の表示・スライド作成は、牧師の画面と同じ部品（`src/ui/`）。**共通の部品に「担当者なら」の分岐は入れない**（選べる対象などはページから渡す）。
- スライドは作る直前に週・マスタ・名簿を読み直す（牧師と担当者が別々にマスタを変えるため。確認ダイアログは作らない）。
- 「週報（PDF）」タブは保存済みの内容（`api/pdf/<日付>`）。Render が眠っていると 1 分ほど。

**記録**: 担当者の書き込みは、変更の記録に `via: "slides"` と担当者のメールで残る（§2.6）。

**配置とプレビュー**: 同じリポジトリで、設定は `slides/wrangler.jsonc`。`main` への push で週報 Worker と一緒に配置される（§1）。

**担当者を足す・外す**: Zero Trust のポリシー `shuho-slides` のメール一覧を直す（ポリシーの画面はカード不要）。担当者に Cloudflare のアカウントは要らない（メールに届く暗証番号でログイン）。

**まだ確かめていないこと**
- 24 MB の pptx を本番の内線で受け渡せるか（手元では確認済み。本番は Worker の計算時間 10 ms の中で指紋を計算できるか）。
- 独自ドメインに載せたときの受付と、`/input-shuho/slides*`（担当者用）と `/input-shuho*`（週報）の割り当ての優先（本番移行のとき）。
- 教会のアカウントでもカードなしで Access が有効になるか（教会のアカウントで最初の Worker を作るとき）。
