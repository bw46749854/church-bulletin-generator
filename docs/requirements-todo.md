## 3. PDF エンジンの切り替え（Cloudflare Browser Rendering ⇄ Render のコンテナ）

**目的** 本番は Cloudflare（眠らない・部品が少ない）、テスト・リハーサル（大量に生成する）は Render のコンテナ（上限なし）。切り替えは設定だけ。Render 使用時は Cloudflare 側の Chromium と**ビルド番号まで**合わせ、違えば知らせる。

**動き**
- Worker の環境変数 `PDF_ENGINE = cloudflare | render`、`PDF_RENDER_URL`、secret `PDF_RENDER_SECRET`
- どちらのエンジンも同じ入出力（HTML → PDF・溢れ一覧・エンジン名・Chromium の版）。応答ヘッダ `x-pdf-engine: cloudflare/128.0.6613.137` / `render/128.0.6613.137`
- 入力画面の状態行に「PDF: Render Chromium 128.0.6613.137（本番 128.0.6613.137 と一致）」のように表示。**不一致なら赤で警告**
- Cloudflare 側の版の取得: `browser.version()`（CDP 経由。UA 文字列は末尾が丸められるが、こちらはビルド番号まで返る見込み → **要確認**）。1 日 1 回だけ起こして D1（`meta/cf-chromium`）に記録（上限をほぼ使わない）。Render 側の版は PDF 生成時の応答に含める
- Render コンテナ: Dockerfile（`ARG CHROME=128.0.6613.137`、Chrome for Testing を `@puppeteer/browsers` で焼き込み、フォント焼き込み、Node、`scripts/pdf-server.mjs`＝`POST /pdf` 合言葉ヘッダ必須・`GET /health`）。版を上げるときは Dockerfile の数字を変えて push（Render が自動再ビルド）
- 眠り対策: `PDF_ENGINE=render` のとき、入力画面を開いた時点で Worker 経由で `/health` を叩いて起こす
- Render が応答しないとき: **エラー表示（2026-09-22 確定）**。自動で Cloudflare に切り替えない（挙動が読める方がよい）

**決め** 起動時に Cloudflare の版へ動的に合わせることは**しない**（眠りから起きるたびに 150MB のダウンロード、比較対象が勝手に動く）。人が数字を合わせる。
**未決**
- Cloudflare の正確なビルド番号（9 時以降に取得して確認）。Chrome for Testing に同じビルドが無い場合は最も近い版
- Render Free の 512MB で安定するか（実測）
- Render の網が Cloudflare を前置きしている件（障害対策としては数えない。項目 5・6 で担う）

## 4. プレビューは PDF.js で描く

**目的** プレビュー＝実際の PDF にする（端末・ブラウザに依らない、本番と同じ折り返し）。iPad Safari（iframe の PDF は 1 ページ目だけ）・Android Chrome（PDF を inline 表示できない）でも同じタブの中で見られるようにする。

**動き**
- プレビュー要求 → Worker が（項目 3 のエンジンで）PDF を作って返す → ブラウザの中で PDF.js が各ページを canvas に描いてプレビュー枠に並べる
- 拡大縮小（ボタン／ピンチ）、「PDF を保存」「印刷」ボタン、溢れ一覧の表示は今と同じ
- PDF.js（`pdfjs-dist`、MIT）は `/input-shuho/vendor/` に自前配置。CDN 接続なし。1〜1.5MB、初回のみ読み込み
- 今日入れた「ブラウザ自身が HTML を描く」プレビューは**外す**（二つの真実を作らない）
- 生成のたびに D1 に 1 行記録（時刻・エンジン・所要秒・週）。無料枠の消費を実測するため。マスタタブか状態行で「今日 n 回・約 m 分」を見せる

**決め** 保存後の表示も同じ描画経路（保存で返る PDF をそのまま描く）。

**PDF の写しを KV に置く（指紋方式、2026-09-22 合意）**
- 描く側に渡す JSON を**その週の印刷に必要な分だけ**に絞る（射影）: 週データ＋その週が使う番号の曲名・交読文＋自教会の牧師 1 件＋祈り課題＋教会情報＋設定・縮小規則。render.js はこれ以外を見られない
- 指紋 H ＝ SHA-256（**描く側に渡した JSON そのもの**（キー順を固定して文字列化）＋ テンプレの版（配置時に決まる）＋ Chromium のビルド番号）。「印刷に影響するものを選ぶ関数」は**別に作らない**（描く側とずれる事故を構造的に防ぐ）
- KV `pdf/<H>` に PDF 本体＋付箋（溢れ一覧・Chromium 版・作成時刻）。tmp/正式の旗は持たない
- プレビュー: H を計算 → `pdf/<H>` があれば返す（生成なし）／なければ生成して置く（有効期限 1 日）
- 保存: 週 JSON を D1 に書く → H を計算 → `pdf/<H>` があれば使う、なければ生成 → 期限を 90 日に延ばし、D1 に「しおり」`weeks/<日付>.pdf → H` を置く。古い H は期限で自然に消える（削除処理なし）
- 帰結: 曲名の修正はその番号を使う週だけ、名簿の追加・肩書変更はどの週も作り直さない、祈り課題・教会情報・テンプレ・Chromium 版の変更は全週作り直し（開いたときに初めて生成）
- 原則との関係: `pdf/<H>` は消えても困らない一時的な写し（正本 JSON から同じものが作れる）。「成果物を保管しない」には反しない

**未決** canvas の解像度（端末の devicePixelRatio に合わせる。2 ページ × 2 倍で十分か）。

## 6. KV・D1 → recovery への取り込み（正本の写し）

**目的** KV・D1 を正として、その全内容を手元に写す。バックアップと recovery の材料を兼ねる。

**動き**
- `scripts/pull.mjs [--remote] [--files] [--bible]`（`seed-d1`／`seed-kv` の逆）:
  - D1 `objects` → `data/church.json`、`data/prayer-list.json`、`data/masters/*.json`、`data/weeks/*.json`（＋`meta/*`、`public/*`）
  - KV → `data/files/`（歌詞 259 本・交読文 64 本・テンプレ・manifest、合計約 32MB）。変更が稀なので `--files` 指定時のみ
  - 聖書 D1 → `data/bible.sqlite`（28MB、静的。`--bible` 指定時のみ。元の `SKY2017.db` があれば `import-bible.mjs` で作れるので必須ではない）
  - 手元の `data/` にあって正本に無いキーは**消さない**（手元で作った未反映の週を守る）。差分を一覧で表示
- 実行者は wrangler にログインした開発者 PC。教会 PC で wrangler を使わせない **[要判断: 教会 PC からも取れるようにするなら、入力画面に「控え一式（zip）をダウンロード」ボタンを付ける方式]**
- 頻度: 週 1 回（手動。開発者 PC は常時起動ではないので自動化は無理をしない）。実行日時を `recovery/PULLED_AT` に残す

**決め（2026-09-22 合意）**
- 正本は KV・D1。**両方作る**: 開発者向け `pull.mjs`（wrangler、リポジトリの `data/` に直接）と、画面向け（Worker が D1・KV を直接読んで返す。wrangler 不要）
- 画面向けは recovery のローカル版に「同期」画面: 「同期状態を確認」→ Worker から一覧（キー・大きさ・指紋・更新時刻）を取り、手元と比べて「正本が新しい／手元にしかない／一致」を表示 → 「取り込む」で差分だけ 1 ファイルずつ上書き（手元にしかないものは消さない）→ 「送る」でオフラインで作った週を正本へ
- 「控え一式（zip）」は JSON データだけ（数百 KB）。pptx は 1 ファイルずつ（Worker の CPU 10ms のため zip に固めない）
- pptx の指紋は**置くときに**ブラウザが計算して KV のメタデータに貼る（一覧作成時に Worker が 32MB を読まない）。既存 323 本は `seed-kv` で付箋を付け直す
- 聖書 D1 は同期対象外（変わらない。変えるのは開発者の `import-bible` 例外作業）
**未決** 週の JSON が `RETAIN_WEEKS` で消える前に写す必要がある → `RETAIN_WEEKS` を 52 以上にする件と合わせて決める **[要判断]**。

## 7. ローカルのファイルを指定して KV・D1 の内容を置換

**目的** 歌詞 pptx の追加・差し替え、テンプレ pptx の更新、名簿 JSON の差し替えなどを、開発者が wrangler を打たずに（将来は運用者が）画面から行う。

**動き**
- マスタタブに「ファイルの差し替え」: ファイルを選ぶ → 置換先のキーを決める → 内容の検査 → 「置換」。置換前の内容は `history/<key>/<時刻>` に残す（取り消し可能）
- 置換先の決め方: ファイル名から自動判定（`123.pptx`→`hymns/123.pptx`、`people.json`→`masters/people.json`、`worship.pptx`→`template/worship.pptx`）し、人が確認して確定。任意のキーは打たせない
- 検査:
  - pptx: zip として開けること。歌詞は `sldSz` で 16:9 かを見て、`manifest.json`（一覧・比率）を更新。**Worker の CPU 制限（10ms）に当たるので、zip の検査と比率判定はブラウザ側で行い、結果だけ送る**
  - JSON: 形の検査（名簿は `{titles, people[{id,name,title,flags}]}`、曲名は `{番号: 曲名}` …）。壊れた JSON を正本に入れない
  - 大きさ: KV 値は 25MB まで（歌詞 pptx は 1 本 数百 KB〜数 MB で問題なし）
- API: `PUT /api/files/<key>`（pptx・xml・manifest）、`PUT /api/objects/<key>`（JSON。既存の `masters/*` 保存の一般化）。**要認証**（ログインを入れるまでは個人アカウントのリハーサルに限る）
- CLI（`seed-d1`／`seed-kv`）は残す（開発者の大量投入用）

**決め** 削除機能は付けない（消すのは開発者作業）。
**決め（2026-09-22 確定）** 名簿は **JSON の差し替え**で行う（名簿編集画面は作らない）。

## 8. ローカル完結の開発環境（2026-09-23 決定）

### 目的（決定）
- **開発のため**。運用（週報を作る）ではない
  - (a) AI エージェントに保守させるとき、Cloudflare にも GitHub にも接続させずに手元で完結させる（無料枠も Access も通らない）
  - (b) 教会内部の協力者が手伝うとき、および無料の AI に PR を作らせたものを手元で確かめるとき
- recovery（障害対策・項目 5）とは**別物**として扱う。あちらは運用、こちらは開発

### データの扱い（決定）
- **教会内部でしか使わないので、実データで問題ない**という整理
  - 名簿（実名 34 名）・歌詞は、内部メンバーに渡してよい。**本番の編集権限も与える**
  - 聖書本文は変わらないので、**一度配置して終わり**（同期の対象にしない）
- 既定はサンプル（`data/examples/`）のままにする。AI に触らせるとき・PR を確かめるときは、何も考えず安全側から始められるように

### 新しい PC で不足するもの（実測 2026-09-23）
Git に入っているのは config / church / people / hymns / readings / prayer-list / texts / 週 1 件。不足は 2 つだけ:

### 構成（案）
`npm run setup` 一本。データの出どころだけ切り替わる:

```

npm run setup -- --data <zip>      運用者が固めたスナップショットを展開
npm run setup -- --pull            正本から取得（合言葉が要る）
```

前提として手で入れるもの: **Node 22 以上**（`node:sqlite` を使うため）と git。ここは OS ごとに違うので手順書になる。

### この決定から出てくる論点（未決）
- **本番編集は人のログインで行う**（ワンタイム PIN → 本番は Google サインイン）。サービストークンは機械用なので人に配らない。
  ただし `pull` は機械の操作なので資格情報が要る。人数が増えるなら**1 人 1 本**（共有すると止めたいときに全員止まる）
- **「誰が変えたか」が残らない**: いま退避は `history/<キー>/<時刻>` で、人が入っていない。
  運用者 1 人の前提では足りていたが、複数人が本番の名簿・歌詞を編集するなら要る。ログイン情報は持っているので 1 項目足すだけ。**人が増える前に入れる**
- PR の確認を成立させるには、環境よりも**テスト**が効く（`npm run setup` → `npm test`）。既存の未決事項「テストをリポジトリに入れる」の**優先度が上がった**

- **Access を掛けたので、いまは同期が動かない**（`pull.mjs`・`dev-server.mjs` とも `CF-Access-*` を送っていない）← 要対応
- 未解決: ①削除が伝わらない（`pull` は手元にしかないものを消さない）②KV のファイルは取り込みのみ ③どちらを正とするかが文章だけ
- **双方向同期は要らない可能性**: 週報は週 1 回・担当 1 人。実際に必要なのは「編集する場所を一時的に移す」（平常＝正本／障害時＝手元／復旧後に戻す）。
  同時編集が起きなければ衝突解決という一番重い部分が消える。保存時の version 照合（409）は既にある

## 9. 属人性の解消（2026-09-23）

### 本当の目的（決定）
**「私以外には何もできない」状態をなくすこと。** 項目 8（ローカル完結の開発環境）はその手段の一つにすぎず、目的ではない。

### 3 つの層に分かれる

| 層 | 内容 | 頻度 | 担い手 | 現状 |
|---|---|---|---|---|
| **A. 週報を作る** | 毎週の入力・PDF・スライド | 週 1 | 運用担当（複数人可） | 画面あり。**ログインが未実装** |
| **B. マスタを直す** | 誤字、曲名、連絡先、名簿 | 気づいたとき | 気づいたメンバー | **画面が半分しかない** |
| **C. システムを直す** | レイアウト、サイト、機能 | 稀 | 誰でも（＋AI） | GitHub にある |

### 層 B — AI も git も要らない
「メンバーに直してもらう」に AI や GitHub を持ち出すと、**かえって属人性が上がる**（PowerPoint が使える人／git が分かる人、と条件が増える）。
正解は**入力画面を完成させること**。条件が「ブラウザが使えること」だけになる。

画面で直せるもの / 直せないもの（実測 2026-09-23）:

```
直せる    曲名（番号→タイトル）／覚えて祈りましょう／教会情報／据え置き文
直せない  名簿        → 「この画面では閲覧のみ。変更は名簿ファイルで」
          歌詞の本文  → pptx を作り直してアップロード（＝PowerPoint が要る）
```

**やりたいことがちょうど直せない側にある。** 必要なのは 4 つ:
1. ログイン（本番は Google サインイン）— **これが無いと B が始まらない**
2. 誰が変えたかの記録 — いま `history/<キー>/<時刻>` に人が入っていない
3. 名簿の編集画面
4. 歌詞本文の編集（pptx の中のテキストを書き換える。JSZip の部品は既にある）

### 層 C — 心理的ハードルが本体（方針転換）
当初「稀にしか起きないことのために全員が git を使える必要はない」と整理したが、**誤り**。
**滅多に使わない手順は、必要になったときには必ず失われている。** 稀だからこそ、ゼロから始められる形にしておく必要がある。

手が止まる理由の内訳:

```
× 書き方が分からない    → AI が解決する
◎ 壊したらどうしよう    → AI では解決しない
◎ 直ったか確認できない  → AI では解決しない
◎ 戻し方が分からない    → AI では解決しない
```

**AI の賢さではなく、可逆性・可視性・隔離が本体。** AI が七割の出来でも、見えて戻せるなら人は試す。逆に AI が完璧でも、戻せないなら誰も押さない。

| 原則 | 具体 |
|---|---|
| 隔離 | 本番に直接触らせない。必ず PR を経由する |
| 可視性 | PR ごとに**本物の URL**でプレビューが見られる |
| 可逆性 | 気に入らなければ捨てる。取り込んだ後も 1 操作で戻る |

### 部品はほとんど揃っている

| 部品 | 状態 |
|---|---|
| 要求を入力する画面 | Worker と Access の基盤がある。薄く載せるだけ |
| PR ごとのプレビュー URL | **既にある**（Workers Builds の非本番トリガー＝`wrangler versions upload`） |
| 本番への配置 | **既にある**（本番トリガー＝`wrangler deploy`） |
| 戻す | git revert → 再ビルド。既存経路の上 |
| PR の作成 | GitHub API。新規だが小さい |
| パッチの生成 | Gemini API。新規 |

### 品質の担保 — md だけでは弱い
設計原則の md は「お願い」でしかなく、守られたか誰も確かめない。3 層で:

1. **触れる範囲を機械的に絞る** → `docs/zones.md`（緑・黄・赤）。判定は**要求の文面ではなく生成された差分**で行う
2. **よくある要求は型にする**（文言を直す／写真を差し替える／ページを増やす／その他自由記述）。型に嵌まるものは AI の自由度を下げ、失敗しようがなくする
3. **通らない PR は出さない**（ビルドが通る・リンク切れなし・表示が崩れない）→ **テストの取り込みがここで効く**
4. **承認は人**。完全無人にすると誰も責任を持たない。「牧師または役員 1 名がプレビューを見て承認」

### 自由記述（残りの 2 割）の内訳
実装が難しいのではなく、**決めることがある**ものばかり:

| 種類 | 例 | 扱い |
|---|---|---|
| 漠然とした見た目 | 「古い感じがする」「スマホで読みにくい」 | **AI が一番得意**。自由記述の主戦場 |
| 新しい仕組み | 行事カレンダー、説教の音声、問い合わせフォーム | 作るかどうかの判断が先 |
| 外部との連携 | 地図の埋め込み、YouTube、SNS | 外部通信・プライバシーの判断 |
| 構造の変更 | メニューの並べ替え、ページの再編 | サイト全体に影響 |
| 公開範囲の判断 | **「過去の週報を PDF で載せたい」** | ⚠ 週報には**実名・献金額・牧師の携帯番号**が載っている |

**型は最初に完璧を目指さず、育てる。** 自由記述で同じ要求が何度か出たら型に昇格させる。
そうすれば型は実際に必要とされたものだけが増え、AI に任せる範囲が減っていく（放っておくと良くなる構造）。

### 層 C の段階（案）

| | やること | これだけで得られるもの |
|---|---|---|
| 1 | PR プレビューの経路を確かめ、README に「PR を出すと URL が出る」と書く | **AI 抜きでも、試して見て戻せる**ようになる |
| 2 | `docs/zones.md` と `docs/ARCHITECTURE.md`（依存の出典） | AI にも人にも効く土台 |
| 3 | 型つきの要求フォーム → PR 作成 | 非エンジニアの 8 割 |
| 4 | 自由記述 → Gemini → PR | 残りの 2 割 |
| 5 | 承認・マージ・戻すを画面から | 一周が画面で完結 |

**1 が最も費用対効果が高い**（AI を使わずに可視性と可逆性が手に入る。1 が無いと 3〜5 は機能しない）。

## 10. 讃頌歌・交読文のマスタと pptx の管理画面（2026-10-21 要件整理）

**2026-10-21 実装済み**（ブランチ ui-10。仕様は ARCHITECTURE.md §14.6）。本番への反映は確認待ち。

**目的** 牧師がマスタに無い番号を使うとき、その場でマスタに登録する。登録しただけでは pptx が無いので、「マスタはあるが pptx が無い」状態が担当者に見えるようにし、担当者が pptx を新規・上書きでアップロードする。

**流れ**
1. 牧師: 週の入力で、マスタに無い番号を入れる → 「マスタ」タブで番号と題を登録する
2. 画面: その番号が「pptx 未登録」と表示される（一覧・週の入力欄・スライドタブ）
3. pptx 担当者: 一覧で「pptx 未登録」を探し、pptx をアップロードする → 「完備」

### 状態（番号ごと。讃頌歌・交読文で同じ）

| 状態 | マスタ | pptx | 表示 |
|---|---|---|---|
| 完備 | ○ | ○ | 枚数・比率・更新日 |
| **pptx 未登録** | ○ | × | 黄色のバッジ「pptx 未登録」 |
| マスタ未登録 | × | ○ | 灰色のバッジ「マスタ未登録」（マスタだけ削除したとき） |
| （どちらも無い） | × | × | 一覧に出さない |

### 対象と操作

| 対象 | 新規 | 更新 | 削除 |
|---|---|---|---|
| `masters/hymns.json`（番号→曲名） | ○ | 題を直す（番号は変えない。変えるときは削除＋新規） | ○ |
| `masters/readings.json`（番号→題） | ○（**今は画面から登録できない**） | 同上 | ○ |
| `hymns/<番号>.pptx`（KV） | ○ | 上書き | ○ |
| `readings/<番号>.pptx`（KV） | ○ | 上書き | ○ |

- **pptx はマスタ登録済みの番号にだけアップロードできる**（決定 1）。マスタに無い番号は「先にマスタに登録してください」で止める。
- 削除は 3 通りを別々にできる（決定 2）: **マスタだけ削除**（pptx は残り「マスタ未登録」になる）／**pptx だけ削除**（「pptx 未登録」になる）／**両方削除**（一覧から消える）。
- アップロードの検査は今の「ファイルの差し替え」と同じ（zip か・`ppt/presentation.xml` があるか・比率・枚数・指紋）。16:9 でなければ注意を出す。
- **マスタの更新・削除は上書き。控え（`history/`）は残さない**（2026-10-21 決定。今の「曲名の登録」と同じ）。
- **pptx の上書き・削除は「アーカイブ＋新規」**: 前の内容を KV の `history/<キー>/<時刻>` に写してから置き換える・消す（上書きは今の動きのまま。削除にも広げる）。アーカイブは画面からは見えず、戻せない。一覧表 `manifest.json` は新規・上書き・削除のたびに直す。
- 新規追加で既にある番号を入れたら「既にあります」と出し、その行を選んだ状態にする（上書きしない）。
- 使っている週があるかどうかのチェックは**今回はしない**（決定 3）。

### 削除のロック

- 削除ボタン（3 種とも）は、ふだんはグレーアウトしていて押せない。
- 一覧の上の「**削除を有効にする**」を押すと押せるようになる。有効な間は一覧の枠を赤くし、ボタン名を「削除を無効に戻す」に変える。
- タブを移ったときは自動で無効に戻す。

### 確認ダイアログ（決定 4: 新規・更新・削除の全部で出す）

| 操作 | 文言の例 |
|---|---|
| マスタ新規 | 讃頌歌 6「父、み子、み霊の」を登録します。よろしいですか？ |
| マスタ更新 | 讃頌歌 6 の題を「（前）」から「（後）」に変更します。よろしいですか？ |
| pptx 新規 | 讃頌歌 6 の pptx を登録します（ファイル名・枚数・比率）。よろしいですか？ |
| pptx 上書き | 讃頌歌 6 の pptx を上書きします（今: 9 枚・2014-11-21 → 新: 5 枚）。前の内容は history に残ります。よろしいですか？ |
| マスタだけ削除 | 讃頌歌 6 のマスタを削除します。pptx は残ります。よろしいですか？ |
| pptx だけ削除 | 讃頌歌 6 の pptx を削除します。マスタは残ります。よろしいですか？ |
| 両方削除 | 讃頌歌 6 のマスタと pptx を両方削除します。よろしいですか？ |

### 画面構成（「マスタ」タブに新しい欄）

一覧＋選んだ行の操作パネル。行ごとにボタンを並べると 260 行×3 つの削除ボタンになるので、操作は選んだ 1 行にだけ出す。パネルは「マスタ」「pptx」の 2 段に分け、それぞれの削除をその段に、両方削除を最後に置く（何が消えるかが場所で分かる）。

```
┌ 讃頌歌・交読文 ─────────────────────────────────────┐
│ [讃頌歌 260 ⚠1] [交読文 64]                               │
│ 表示 (●すべて ○pptx 未登録 1 ○マスタ未登録 0)  番号 [    ] │
│ 新規  番号 [   ] 題 [                  ] [登録]             │
│                                        [削除を有効にする]  │
│ ┌番号┬題──────────────┬pptx───────────────┐│
│ │  6 │父、み子、み霊の      │⚠ pptx 未登録              ││
│ │  9 │聖なる、聖なる、聖なる│9 枚・16:9・2014-11-21     ││
│ │ …  │                      │                           ││
│ └──┴───────────┴──────────────┘│
│ ── 讃頌歌 6 ───────────────────────────────── │
│ マスタ  題 [父、み子、み霊の        ] [題を更新] [マスタだけ削除]│
│ pptx    未登録  [ファイルを選ぶ] [アップロード]   [pptx だけ削除]│
│                                                  [両方削除]│
└───────────────────────────────────────┘
```

ボタンが押せる条件（削除は、さらに「削除を有効にする」の後だけ）:

| ボタン | 押せる条件 |
|---|---|
| 題を更新 | マスタあり、かつ題を変えた |
| アップロード | マスタあり（pptx の有無で「新規」「上書き」を文言で区別） |
| マスタだけ削除 | マスタあり |
| pptx だけ削除 | pptx あり |
| 両方削除 | マスタも pptx もある |

「マスタ未登録」の行では、アップロードの代わりに「先にマスタに登録してください」と出す（上の新規欄に番号を入れた状態にする）。
選んだ行の pptx は「開く」でダウンロードできる（今の `GET api/files/...` を使う）。

### 「pptx 未登録」を見せる場所

1. **一覧**: 状態のバッジ、絞り込み、種類の切り替えに件数（「讃頌歌 260 ⚠1」）。
2. **週の入力欄**: 番号の横の表示を 3 通りにする。マスタなし →「曲名が未登録（『マスタ』タブで登録）」（今のまま）／マスタあり・pptx なし →「（曲名）pptx 未登録」／完備 →「（曲名）」。
3. **スライドタブ**: 作る前に、その週で使う番号のうち pptx が無いものを出す（「讃頌歌 6（賛美 2）の pptx が未登録です」）。今は作った後の注意でしか分からない。

### 既存の機能の整理

- 「マスタ」タブの今の「曲名の登録」欄は、この画面に置き換える。
- 「ファイルの差し替え」の置換先から、`hymns/<番号>.pptx`・`readings/<番号>.pptx` を外す（入口を 1 つにする）。`masters/hymns.json`・`masters/readings.json` の丸ごとの差し替えは、一括の復元用に残す。
- 画面は最初に読むデータ（`api/bootstrap`）で pptx の有無を知る必要がある → 番号の一覧（`manifest.json` の hymns・readings のキー）を加える。

### API（案）

| 口 | 動き |
|---|---|
| `POST api/masters/hymns`（今ある）・`POST api/masters/readings`（新設） | 追加・更新 |
| `DELETE api/masters/hymns/<番号>`・`DELETE api/masters/readings/<番号>` | マスタの 1 件を削除 |

「両方削除」は画面から 2 つの DELETE を順に呼ぶ（pptx → マスタの順。途中で失敗しても「マスタ未登録」は残らない）。
